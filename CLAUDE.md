# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Calltrainer is an AI-powered phone conversation trainer that provides real-time analysis and behavioral feedback during simulated calls (from README.md).

## Current State

FastAPI backend (`backend/app.py`) serves the API and, once built, the React + TypeScript frontend (`frontend/`, built with Vite; the backend serves `frontend/dist`). The SPA has a router (`react-router-dom`, paths in `frontend/src/routes.ts`): `/` is the training flow, `/profil` the account screen, `/trainings/:sessionId` one past training, and `/impressum`, `/datenschutz`, `/barrierefreiheit` the legal pages the footer links (`components/legal/`, shared frame in `LegalPage.tsx`). Imprint and accessibility statement are the EFRE DiReKT project's own texts, adopted unchanged apart from one scope sentence; the privacy statement is adapted to what this application actually processes; the draft banner and the two gaps the first draft carried (KugelAudio's seat and DPA, the server's location) are **filled in**, and what is still outstanding is **review by the data protection officer**, which no code change can supply. `/hinweise` carries the AI disclaimer (you are talking to a machine, it invents things, the wrap-up is not an assessment, do not say other people's data aloud). The privacy statement names the real processors: Hetzner Gunzenhausen as hoster and KugelAudio UG Hannover for the speech output, both under Art. 28 agreements, with KugelAudio's own sub-processors in Germany and Finland. **ADR 0020 says the deployment is a university server; it is actually Hetzner** — the ADR carries a status update saying so. DPO review of the privacy statement is still outstanding. The profile screen carries the history (F-48): `useSessionHistory` reads `GET /api/sessions` one page at a time and appends on demand (de-duplicating by id, because offset pagination shifts rows when a Session is written mid-browse), `SessionHistory` renders one row per training, and a row links to `PastSessionView`. What is *shown* is capped separately from what is held: three rows to begin with, then ten per press (`FIRST_ROWS`/`STEP_ROWS`) — the list sits under the account and the consent switches, so it opens as a glance rather than as a page. Every row carries its own delete control — a bin button *beside* the link, never inside it (a `<button>` nested in an `<a>` is invalid and would navigate as well), which opens an inline confirmation under that row and, on success, drops the row locally via `useSessionHistory`'s `removeSession` rather than refetching, because re-requesting the same offsets after a row disappeared would skip one. `showMore` asks the server for the next page only when the rows it is about to reveal are not already here, and one step is smaller than one page, so a press never waits on more than one request. That screen reads the Session **once** (`useStoredSession`) and never polls — the polling in `useSessionFeedback` is right only for a call that just ended, where a wrap-up genuinely is on its way (ADR 0019); on a days-old Session it spent a minute claiming one was being created and then called it a failure. `FeedbackView` is therefore split into the polling wrapper (unchanged for the live flow), a presentational `FeedbackReport`, and a `MetricSection` — a stored Session with no wrap-up still shows its Kennzahlen and Transcript, because those are in the database regardless. The two screens are now literally **one component** — `FeedbackScreen.tsx` (which is what `TranscriptView` became) renders the title block, the meta row, the report it is handed, the actions row and the collapsible Transcript for both, and they differ in nothing but the buttons: "Zur Startseite" against "Zurück zum Profil" (which the history's page also repeats *above* the report, so a reader who has changed their mind after the first paragraph does not have to scroll a page of feedback to get back), and the deletion passed in as children. Everything short of that kept drifting while they were two pieces of markup — a different column width, then a different title, then a plain-list Transcript against a panel that opens. The meta row (case · partner, or "Rollentausch: Sie riefen an, X nahm ab") moved out of `FeedbackReport` in the same step, because it describes the *call*: a Session whose wrap-up never got written still has a case and a partner, and the history was the only screen that said so. The history's page keeps the header's step indicator off, though — a past training is not a position in the training flow. Note that a missing wrap-up is **not** missing for want of audio: the generator works from the Transcript and the stored Measurements (ADR 0049), so a Session stuck on `queued`/`failed` can still be generated later — `scripts/requeue_feedback.py` is that path, and its dry run needs only Postgres. Because those paths exist only in the browser, `app.py`'s `SinglePageApp` falls back to `index.html` for unknown paths — but never under `/api`, `/ws` or `/health`, and never for a path that looks like a file, so an unknown endpoint stays a 404 instead of answering a script tag with HTML (`tests/test_spa_routing.py`). Keycloak always redirects back to the origin, so returning to the requested page is the app's job: `onSigninCallback` in `main.tsx` strips the `?code=&state=` and stores the path, and `<ReturnToRequestedPage>` navigates *through the router* — `history.replaceState` fires no event a router would hear, which is the trap here. The header's brand link and account chip are suppressed during the mic check and the call (`navigationLocked`): leaving the page tears down the WebSocket, and an abandoned Session is never persisted (ADR 0034). The chip is `visibility: hidden` there rather than dropped from the markup — it keeps its width, so the progress steps do not shift sideways on the way into a call, and `visibility` takes it out of the tab order and off the screen reader as well. The wordmark is one component (`BrandName.tsx`) everywhere it appears, so the orange "ai" cannot drift between the header, the login screen and the redirect card; `--color-brand-accent` sits deliberately under 4.5:1 on white, which WCAG 1.4.3 allows for a brand name and for nothing else — do not reuse it for ordinary text. The browser icon is `frontend/public/favicon.ico`, five bitmaps in one file, all five showing the whole logo on an opaque white ground. The **16 and 24px entries are hinted rather than downscaled**: at those sizes the waveform bars fall under a pixel each and a plain resample blurs them into one grey block (which is why those two sizes used to drop the bars and show a bare headset). They are built instead from the headset alone — its strokes grown a little first, so a ring thinner than one target pixel still lands as a line — with the five bars drawn straight onto the pixel grid at the logo's own measured proportions (17/36/56/36/17 percent of the motif's height), between the earcups where the logo puts them. `logo.png` is 256px for a largest display size of 58px, so it is no longer a source for anything bigger; both it and the icons are regenerated by hand when the logo changes, there being no script for it in the repository. The profile screen is read-only by construction — identity lives in Keycloak and there is no local User table (ADR 0031), so it renders ID-token claims via `useAccount` and says so; it carries the F-49 privacy notice, the consent and retention switches, **the Fokusziele section (F-62, below)**, the data overview, and a deletion section that names the three real paths (one training from its row in the history or from its own page, all of them by withdrawing consent, the whole DiReKT account by mail) and, per ADR 0070, says which of them takes the Rollentausch rows with it — the withdrawal does, a single deletion does not. **Fokusziele (F-62, ADR 0076)**: a User picks **at most five** training focuses from a shipped catalogue of 14 in 4 groups — asked once at first start (`FocusDialog`, and **Ohne Fokus fortfahren** is a full answer), changed afterwards in the profile (`FocusSettings`); both render the same `FocusGoalPicker`. Three tables: `focus_goal` is a reference table seeded from `seed_data.py`'s `FOCUS_GOALS` (German display text lives in the row, like a Scenario's title; retired rows are deactivated, never deleted), `focus_selection` records *that* a subject answered — its own row, because "picked nothing" and "was never asked" must be distinguishable or the dialog re-opens forever — and `focus_selection_goal` holds the picks. **"Souveräne Lautstärke" was retired** (ADR 0076's amendment): what `acoustics.py` measures is the level of the recording, which is the microphone and the distance to it as much as the speaker, so two calls by the same person are not comparable — the Kennzahl `loudness` stays for the single call, the goal does not, and `api/focus.py` drops a retired key from the *served* selection (the row stays) so it cannot hold one of the five slots with no card on screen. `backend/focus.py` is the single place all three are read and written, always scoped to the caller's `sub`; `MAX_GOALS = 5` is enforced there (a sixth goal is a **400**, never a silent truncation) and travels to the client in every `/api/focus` payload, so the picker disables the sixth checkbox using the backend's own number (ADR 0063's pattern). `GET /api/focus` serves catalogue *and* selection in one response — the dialog needs both and two requests would render half a state; `PUT /api/focus` replaces the whole set (hence PUT, unlike `/api/consent`, which appends). Every goal carries `evidence` (`measured` / `mixed` / `interpretive`), which records how far it is derivable today and **stays internal** — not on the wire, not on a card: the aim is that every goal becomes measurable, and asking the User to weigh that up while picking would push an implementation detail into their choice. The obligation it stands for moves to whatever eventually *reports* on a focus, which may only claim what is actually behind the goal (ADR 0004/0051). A focus is a **setting, not training data** — no consent guard (declining consent must not also cost you the setting) and `deletion.py` deliberately never touches it, which a test pins. `FocusProvider` nests inside `ConsentProvider` in `main.tsx` so the two first-run questions come in order, legal one first, and neither blocks on a *failed* load. **What reads a selection** (ADR 0076's amendment): the progress view's top block and the Scenario suggestions below; the wrap-up prompt still ignores it, and anything that comes to report on a goal inherits the constraint that it may only say what the goal's `evidence` allows. Beside the goals a selection carries a `role` (`TRAINING_ROLES`, CHECK-enforced; the German names and the call types each role preselects in `seed_data.TRAINING_ROLE_CATALOGUE`) and the call types themselves (`focus_selection_category`, the `scenario.category` vocabulary), asked on the same first-run screen (`FocusProfilePicker`) and replaced with every `PUT /api/focus` — leaving them out means none. `backend/recommendations.py` makes at most five suggestions from them: 2 for a matching call type, 1 per picked goal whose context it exercises (`GOAL_CATEGORIES`; voice goals steer nothing, since every Scenario trains the voice), unplayed first on a tie, never a reverse or an uncategorised Scenario. The listing marks them with `recommendation: {call_type, goals}` on the card, and that is a **view, not a group**: a suggested card keeps its origin and appears under both. Suggesting a Scenario claims no measurement, so the `evidence` constraint is not touched. **After a call**, `GET /api/scenarios/{id}/next?persona=` (F-64, ADR 0087, `recommendations.next_calls`) offers at most two *existing* Scenarios, each started with one press: the same one with the other-language Persona (never for a reverse, whose brief is German prose), and the best unplayed suggestion from the profile, else an unplayed one of the same category. It needs no stored Session, so `FeedbackView` shows the `NextCalls` block without a wrap-up too; with one, it sits under the follow-up/reverse row. Starten goes through `handleStartFollowUp`, skipping the mic check. With two seeded Personas, one per language, "another partner" and "another language" are the same offer until more are added. Offering by weakness is not built yet; the wrap-up's points carry a focus goal since ADR 0080, which is what it would read. `/health` is liveness only (touches nothing, so a brief database outage cannot look like a dead process) and `/health/ready` is readiness (checks the database) — the compose healthcheck asks the latter, because an instance that cannot reach Postgres can only answer 503. `/api/personas` and `/api/scenarios` (their own routers, `backend/api/personas.py` / `scenarios.py`) list the Persona/Scenario options shown before a Session starts — any Persona can run any Scenario, no compatibility to filter by. **Both read from the `persona`/`scenario` tables, not from Python lists** (ADR 0041), and serve only rows with `active` set: `backend/personas.py` and `backend/scenarios.py` hold the value types only — their hardcoded lists are gone; the seed content lives in `backend/db/seed_data.py`, and `backend/library.py` is the single place the tables are read, written and mapped onto those types. Rows dropped from the seed are deactivated rather than deleted — `session` references them by foreign key, so a past Session has to stay readable. **Users author their own Scenarios** (ADR 0024 → ADR 0058), but **not Personas** — a Persona is a curated character with a fixed voice, so `/api/personas` stays read-only. Each Persona also carries a **portrait**: `persona.avatar_url` holds a path into the frontend's own static files (`frontend/public/personas/<seed id>.webp`, square, face in the upper third), not the image — the pairing is in the table so a new Persona is still a seed change plus a file, and `tests/test_persona_scenario_library.py` pins both the naming rule and that the file exists. It rides on both persona routes and is shown in all three places a Persona appears: a 3:4 portrait down the left edge of the selection card, as tall as the card is (fixed width, stretched height — in a flex row the main size resolves before the cross size, so an `aspect-ratio` driven by a stretched height has nothing to compute from), cropped to head and shoulders by a CSS zoom, since the whole half-body shot is unrecognisable at that size, 160px square in the info panel's header, where the name, role and language sit beside it (which is why `role` is no longer a section further down — it would say the same thing twice), and as the round 160px avatar on the call screen. Nullable and decorative (`alt=""`, the name is always beside it); `frontend/src/components/PersonaAvatar.tsx` is the one place that renders it and falls back to the Persona's initials for a missing path or a missing file. Every Scenario also carries a **`briefing`** (ADR 0054, built): the display text addressed to the *User* — the role they answer in, the room they have, what a good outcome is — as against the four prompt fields, which brief the caller. It rides on the card (`GET /api/scenarios`), is rendered by `frontend/src/components/ScenarioBriefing.tsx` on the setup screen once a Scenario is picked *and* again on the mic check (the screen ADR 0054 names: the Session is already committed to there, so it costs no step), and it is **never** read by `backend/session/prompting.py` — an objective handed to the caller is one the caller pursues, which is exactly the defect ADR 0045 removed; `tests/test_system_prompt.py` pins that. It is optional, and the follow-up generator writes it as a seventh field. Authoring (ADR 0058): each row carries `created_by` (Keycloak `sub`, NULL for a built-in), `visibility` (CHECK-enforced) and an unguessable `extern_id` (ADR 0050) — which is what the client sends in `session.start`, never the `key` slug (nullable now). `POST/PATCH/DELETE /api/scenarios` and `GET /api/scenarios/{id}` are owner-scoped by the verified `sub`; a 404 and a 403 are the same answer. `POST /api/scenarios/document` (F-58, `backend/documents.py`, `pypdf`) extracts the text from uploaded **text-layer** PDFs (no OCR) and has the LLM (`llm.complete`) condense it into a short German fact list for the editor's Fakten field — stateless, the files are never stored; `summarised: false` in the response means the LLM was down and the raw truncated text came back instead. **Several PDFs go in one request** (the form field is `files`, repeated) and are condensed **together, in one model call** — the field holds one list, and two documents summarised apart would repeat every fact they share; `merge_document_text` labels each with its file name (sanitised through `clean()` like any authored text, ADR 0059) so the model can tell them apart, while a lone document is still handed over bare. Two memory ceilings, both in `documents.py`: `MAX_UPLOAD_MB` (5) per file, checked against the declared size *before* reading, and `MAX_TOTAL_UPLOAD_MB` (20) for the request, checked against the bytes actually read *after* each one — so a client that sends no Content-Length still cannot get a second oversized file past the gate. One unusable file fails the whole batch and the message names it (only when there was more than one, so the single-file sentences are unchanged). The editor takes them by picker or by **drag and drop**, and the two ways of filling the Fakten field sit **side by side under its one label**, each on half the row with an *oder* between them (`.facts-split`): the textarea left, the drop zone right — a cloud, "PDFs hierher ziehen", "Dateien durchsuchen", a solid border and 200px tall, because a drop target the height of a button is hard to hit with a dragged file and because stacking the two would read as a second step rather than an alternative. The zone is itself the `<label>` for the hidden input, so a click anywhere in it opens the picker while the keyboard still has a way in — which is why the focus ring is drawn by the zone (`:focus-within`) and not by the input. `case_facts` is therefore the one field `ScenarioEditor.tsx` renders off the generic branch. Both ceilings are mirrored client-side to refuse an oversized drop without sending it — a courtesy check, the server's answer being authoritative, kept the way `FALLBACK_FIELD_LIMITS` is — and the MB figures appear **only in that error**: there is no standing hint under the field naming them, an upload that fits needing no warning about one that does not. While the editor is open a `dragover`/`drop` on `window` is swallowed, because a file dropped beside the zone would otherwise be *opened* by the browser and take the unsaved draft with it. Deliberate simplification over ADR 0005/0024's "uploads route through the Data Platform". The **second** way an authored Scenario comes about is the *Folgeszenario* (F-60, ADR 0069, `backend/followups.py`), and since **ADR 0069's amendment the User asks for it** — `POST /api/sessions/{extern_id}/follow-up`, beside the reverse's route and deliberately identical to it. It was written by the Feedback worker unbidden until then; the amendment argues that the objection which killed the original button was to *not storing*, not to the button. The LLM drafts from the wrap-up's `improvement` points and it is stored through `library.create_scenario` like anything hand-authored — `created_by` = the caller's `sub`, `visibility` = `private`, `tenant_id` the caller's company (a *request* resolves one, which the worker never could). No points is a 409, an unreachable model or a reply that yields no usable draft a 503 with a sentence in it — where the same failure used to be a log line nobody read. `generator.py` no longer calls it, so the wrap-up job has one model call and one way to fail, and `useSessionFeedback` no longer polls past the wrap-up for anything. Provenance is the new `scenario.derived_from_session_id` (nullable FK, indexed, **UNIQUE** so `scripts/requeue_feedback.py` cannot produce a second — though since the amendment that script writes no follow-up at all), and the card carries `follow_up: boolean` beside `origin: "own"`, the pattern `shared` uses. A follow-up leaves the library when its Session goes — one training deleted, consent withdrawn, or the six-month sweep — as `active = False`, never a row delete, because a later Session may have been played on it and `session.scenario_id` is NOT NULL (ADR 0026). `backend/deletion.py::retire_follow_ups` is the one place that decides that; the FK's `ON DELETE SET NULL` clears the provenance beside it. No consent guard is needed anywhere in this path: no consent → no stored Session → no Feedback → no follow-up. Since **ADR 0069's second amendment** the draft is the *next call in the same matter*, not a new situation in the same subject area: the prompt is given the played Scenario's four fields (`description`, `case_facts`, `call_goal`, `success_condition`) plus the wrap-up's `summary` — where that call ended up — and is told to carry the case forward, keeping its anchors and saying what was agreed, what has happened since and what is still open. Handing over a built-in's case is the exception **ADR 0070** already takes to ADR 0043 for the reverse, on the ground that the User has just heard it played out; what stays out is the measured statistics (a Scenario correcting a figure needs the target range ADR 0051 declined to invent). `success_condition` still sits at exactly the improvement point, which is what keeps this an exercise rather than a re-run. The prompt keeps the exercise's purpose out of those four fields, since they become the simulated caller's briefing and a caller who knows what is being trained gives the answer away — the caller may refer to their own earlier call, never to it as an exercise; the card may say it, and the card never reaches the prompt. A follow-up is playable against any Persona like any other Scenario, but it is **neither editable nor shareable** — the same exclusion a reverse carries, for the same reason one step on: it is drafted to sit exactly at the wrap-up's improvement point, so an edited one is no longer the exercise that reading produced, and a shared one would pass on a reading of the author's feedback. `library.py` excludes both kinds in the WHERE clause of `update_scenario` and `set_scenario_visibility` (`_AUTHORED_ONLY`), so PATCH and the visibility toggle answer 404; `_detail`'s `editable` says so to the client, and the detail route carries `follow_up` beside `reverse` for it. DELETE takes both — removing it is the one action left, offered as **Löschen** in the info panel behind the card's "i", exactly where a reverse's is. Both routes share their shape down to the status codes and are idempotent through a UNIQUE column (`derived_from_session_id` / `origin_session_id`), so a second press returns the row the first one wrote — reactivated if the User had removed it — without a second model call; `tests/test_followup_scenario.py` and `tests/test_reverse.py` are deliberately the same shape, so a divergence shows up as a difference between the two files. The **third** thing built out of a finished Session is the *Rollentausch* (F-61, ADR 0070, `backend/reversals.py`), asked for the same way and the pattern the follow-up was moved onto: `POST /api/sessions/{extern_id}/reverse` replays **that** call with the roles swapped — the User rings, the Persona picks up and takes the side the User held. It stores a `scenario` row too, but where a follow-up is *written from* a Session this one *replays* one: it carries the played case **verbatim** plus `reverse`, `origin_session_id` (UNIQUE, so the button is idempotent; `ON DELETE SET NULL`, so the row outlives the training it replays) and `reverse_brief`, the German briefing the User reads *during* the call. A row is at most one of the two, and `_origin_group` in `api/scenarios.py` gives each its own place in the listing. That briefing is one `llm.complete_json` turning the four prompt fields (plus the improvement points, where a wrap-up exists) into prose addressed to the User, and it **translates rather than invents** — they are about to argue this case. It is generated once, stored, and **never put in a prompt**. Two ADRs are suspended on purpose and only here: the played case reaches the client (against ADR 0043, because seeing what the Persona had *is* the feature, for a call the User has just heard play out), and text is shown during the live call (against ADR 0033, because it is the User's own briefing, fixed before the call, never the Persona's lines) — *beside* the state animation, the two sharing the screen 50/50 above 1080px (`call-layout-with-brief`; the page widens to 1240px from the usual 800px) and stacked below that, at **full length with no scrollbox of its own** — a panel with an inner scrollbar hides part of a briefing behind a gesture, and the User not finding a fact they were told they have is the one thing that must not happen mid-call. The brief's `goals` are the call's agenda — concrete things to raise, ask or come away with, each tickable once it has happened, and the prompt rules out advice about tone by name — rendered as a checklist whose count is the User's own tally and never a score (ADR 0004/0065). A reverse is `origin: "own"` but, unlike a follow-up, is neither editable nor shareable — `library.py` excludes it in the WHERE clause, so both answer 404 — and it sits under its own **Rollentausch** filter, so "Individuell" now means hand-authored and nothing else. Deleting one is offered in the info panel behind the card's "i", as **Löschen** — the card itself carries no affordance but that "i" (ADR 0062), and the editor, where every other authored row is deleted, is closed to a reverse. Same word, same corner of the same actions row and same `window.confirm` as the editor's, so the two derived kinds are deleted alike. It asks first because one slip costs a row that can only be recreated from the training it came from, at the price of a model call, if that training is even still stored. The casting is swapped in the *one* system prompt (`session/prompting.py`), not a second one: `_casting`, `_case_block`, `_persona_block` (the Persona keeps name, traits and behaviour, loses `role` and its objections — every seeded role is a customer's), `_no_restart_rule` and `_closing_rules` each have a reversed form, the Persona still speaks first but says only how someone answers a phone (`answering_examples` per LanguagePack). Two things outside `prompting.py` turn around with them, both because they sit *nearer* the reply than the system prompt does and would otherwise undo it one Turn at a time: the settlement check (ADR 0073) and the per-turn anti-repeat nudge (`ANTI_REPEAT_NUDGE_REVERSE`, ADR 0038), whose ordinary form forbids putting a solution forward — which reversed is the Persona's job. The call-state notes (ADR 0071) have a reversed form too, used only where they are used at all. The offer to create one sits under the wrap-up on the post-call screen **and** on a past training's page, which hands the pairing to the training flow through `TrainingStart` exactly as the follow-up's Starten does — a reverse is written on request, so it can be asked for about a training read weeks later. The two offers share one row 50/50 (`.next-steps`, `auto-fit` so a lone one still fills it): they are alternatives, and stacked the second reads as what follows the first. **Neither is shown at all under three User utterances** (`MIN_USER_TURNS` in `FeedbackView.tsx`, counted on `turn.speaker === "user"` — `turns` is one row per speaker, so the Persona's greeting does not count towards it): both build an exercise out of *this* call, and a call hung up after a sentence has no place for one to carry forward from or replay. Starting a reverse — from the wrap-up, from a past training, or out of the microphone check — plays a card-turn cut into the briefing screen (`ScreenTransition.tsx`, mounted above the routes in `main.tsx` because the page that asks for the cut is usually the page the cut navigates away from; the card in `ReverseCard.tsx` is that game's own reverse card recoloured into the DiReKT palette — blue-600 face, navy-900 shadows, the printed card's white border put back around it; blue and not navy because it is shown against a navy scrim. A hand-drawn SVG imitation and the unaltered artwork each held this slot before it. The shape and the symbol are still that game's, which matters beyond the pilot; `scratchpad/make_card.py` is how it was built). The screen changes at the covered frame, and `prefersReducedMotion` (`utils/motion.ts`, shared with F-62's die) skips the animation while still performing the change — a dropped cut would leave the press without an effect. Both take **two presses**: the first writes the Scenario (a model call and the better part of a minute), the second starts the call — the button that begins a conversation must not be the one pressed before there was anything to begin. The wrap-up labels the Persona's turns `Agent` and says the trainee did the calling; measurements are untouched, being symmetric. **Withdrawing consent hard-deletes a subject's reverse rows** (`deletion.py`, ADR 0070's addendum to ADR 0066) because the briefing comes from their own feedback — unlike a follow-up, which is only deactivated. Guard tests pin the ordinary system prompt and the ordinary wrap-up prompt byte-identical. Prompt safety (ADR 0059): authored text is sanitised at the write boundary (`backend/authored_text.py`) — `[CALL_END]`/bracket-token/fence-run stripping — and an authored Scenario adds one prompt line (`AUTHORED_SCENARIO_NOTE`) framing its text as information, not instructions. Company sharing (ADR 0060): `tenant_id` (the author's company, resolved per request in `backend/tenants.py` from a `tenant` claim — a Keycloak user attribute an admin sets at account creation, put in the token by the `calltrainer tenant` protocol mapper; no claim, or an unknown value, means the seeded `default` tenant), `visibility` widened to `private | tenant | public` with a second CHECK tying `tenant` to a non-NULL `tenant_id`. `backend/library.py` scopes every Scenario read to the caller's `sub` + `tenant_id`; the client never supplies either. Sharing is one `PUT /api/scenarios/{id}/visibility` toggle (`private` ↔ `tenant`; `public` needs review, not built). `GET /api/tenant` returns the caller's resolved company name (or `null` for `default`) so the setup screen can show the five scenario filters — **Alle / Standard / Individuell / Folgeszenario / `<Unternehmensname>`**, where "Individuell" means hand-authored — and badge company scenarios with the real name. Post-call analysis lives in `backend/feedback/` and produces **one set of statistics per stretch of a call, never per Turn** (ADR 0051, narrowed by ADR 0081 — the whole call is still the stretch every figure on screen describes, and two more are measured beside it, see F-62's Souveränität below): F-53's Kennzahlen — Redeanteil, Fragen, Sprechtempo, Wortanzahl, Reaktionszeit, Sprechpausen — plus F-37's loudness curve, F-35's Sprachmelodie. That one is **five figures, not one** (`backend/feedback/intonation.py`): Umfang (5th to 95th percentile in **semitones**, not Hertz, so the same expressive range reads the same for a low and a high voice — and the better-supported scale rather than merely the conventional one: on exactly this task Nolan 2003 puts semitones slightly *ahead* of ERB-rate and both far ahead of Hertz, so the ERB scale Hermes & van Gestel preferred for prominence does not apply here), Bewegung (semitones per second, which is what separates a wide-but-drifting contour from a lively one; computed **per utterance and pooled**, never across the flat call contour, because the last frame of one utterance and the first of the next are neighbours in that array and a Persona turn apart in the call, and on a **30 ms median-smoothed** contour, since 2% frame-to-frame tracker noise inflated the raw figure by a third while smoothing costs the real movement 5%), Satzenden (falling/rising/level per utterance, read by least-squares slope over the last 400 ms of *voiced* frames) and Verlauf (first vs last third of speaking time). The endings carry an interpretation because a slope has a natural zero, and their level threshold is **derived rather than chosen** (ADR 0077): below the glissando threshold — `GLISSANDO_ST_S2` = 0.32/T² ST/s for *continuous* speech, Mertens 2004, where 0.16 is the isolated-vowel figure and keeps glides nobody hears — a movement is not heard as a movement at all, which across the 400 ms window comes to 0.8 semitones, where a hand-set 2.0 used to sit at two and a half times the perceptual floor. **The reading sits on the Lebendigkeit and no longer on the Umfang (ADR 0077).** That fifth figure is Hincks (2005)'s pitch variation quotient — SD over mean of F0 in *Hertz* (a dimensionless ratio, so it normalises across voices the way the semitone conversion does), per 10-second window and then averaged (`PVQ_WINDOW_MS`), windowed because a quotient over the whole call counts the drift *between* utterances as movement inside a phrase — read on **three steps**, monoton / lebendig / sehr lebendig at 15 % and 25 % (`intonation.liveliness`, `liveliness_steps`). Still the second deliberate exception to ADR 0004/0051 beside the traffic light below: asked for explicitly, presented as an *Einschätzung* with its whole scale visible and the current step marked, and kept off the dashboard. It moved because a literature review found **nothing behind the old derivation** — the five steps at 4/7/12/18 semitones came from quoted F0 standard deviations converted to a 5–95 span at ≈3.3 SD, and no source states the span figures, the log-F0 distribution that conversion assumes, or anything at all for German; two guesses stacked on each other wearing a citation. Hincks's boundaries were at least measured against human liveliness ratings (r = 0.83 over nine windows) — on 18 Swedish students presenting in L2 English on a room microphone, which the interface now **names**, because "not validated for this user group" without saying what it *was* validated on is not a caveat. **The classification carries a traffic light** (`intonation.LIGHTS`, ADR 0077): monoton **rot**, lebendig **grün**, sehr lebendig **gelb** — where the yellow is *not* a claim that expressiveness is a fault (nothing supports that; above 25 % is simply where the liveliest speakers in Hincks's corpus sat) but marks the one region where the *figure* is least trustworthy, since an octave error inflates a standard deviation badly and nervousness and disfluency produce high variation too; the text says "worth a look at the contour", never "too much". The colour goes on the **classification and never on the semitone figure**, since the step is read from the Lebendigkeit and the Kennzahl's number is the Umfang; on the wrap-up tile that needs no special case, because that tile already leads with the word for Sprachmelodie (ADR 0088). It travels as `liveliness_light` beside `liveliness_label` from beside the threshold, and the frontend maps no step to any colour of its own. **Both lights are governed by ADR 0078**, which is where to look before adding a third. It exists because two exceptions are a pattern, not two exceptions: the wrap-up hands the reader nine figures at equal weight and colour is the only channel that says which to read first, so the light **points rather than grades** (green = nothing here needs attention today, *not* "well done"; red = look here first, *not* "you did badly"). Its seven conditions: colour on a **classification** never on a raw figure; the **whole scale visible** in the user's unit with the current step marked; **never colour alone**, the step is always written out in words; **"Einschätzung"** beside it plus the population the boundaries came from; **colour and wording served from beside the threshold**, never mapped in the frontend; the **direction each colour claims written down** where the constants live; and **single-call only**. ADR 0078 amends ADR 0004 and ADR 0051 (whose "no target range on a raw figure" stands untouched: `metric_type` still has no target column) and leaves **ADR 0065 explicitly unchanged** — no colour on the progress view, none across Sessions, no aggregate colour for a call or a user, which would be a score with a palette. The step is **not stored** with the Measurement — `api/sessions.py::_served_detail` derives it on every read, which is exactly what let the scale be replaced with no migration; a Session measured before `pvq` existed therefore shows **four figures and no step**, because reading it off the stored Umfang would reinstate the withdrawn scale under a new name and the audio is gone (ADR 0048). Bewegung stays a figure with no adjective — the better discriminator in principle, but nothing published anchors a boundary for it. A step needs `MIN_VOICED_MS_FOR_READING` (10 s) of **voiced** speech under it, which is two to three windows against the nine Hincks's reliability figure rests on: a floor, not a sufficiency. Two defects found by audit and fixed: the pitch was analysed on the loudness curve's **100 ms grid**, which aliases intonation (a 16-semitone contour read as 14.2 at 3 Hz and 4.8 at 8 Hz) — it is now Praat's 10 ms, thinned to 100 ms only for the stored curve; and a single fixed floor/ceiling admitted octave errors (a 116 Hz voice produced a 483 Hz frame) — now a **two-pass measurement**, the second pass windowed on the first pass's own quartiles (De Looze & Hirst) — 0.75·q1 to **2.5**·q3, Hirst 2011's later ceiling and not De Looze's 1.5, which sits below an expressive speaker's own rises and produces systematic octave *halving*; the two figures are a real disagreement in the literature and this application records people arguing a case on the telephone (ADR 0077). **The whole reading sits on the Kennzahl's own page** (`IntonationReading.tsx`, rendered by `SessionMetricView` under the figure and the scale — *not* by `MetricSection`, which carries a tile for it like every other Kennzahl; the tile is what leads with the coloured word). That block is deliberately slim (ADR 0077): the contour, then **one lead sentence** with the coloured classification and what it sounds like to the other side, then the *Passte der Ton zum Anlass?* block (ADR 0079, only where a wrap-up wrote one), then the five figures as **tiles in the Kennzahlen grid** (`.melody-grid`/`.melody-tile`, reusing `.metric-grid`/`.metric` so they read as the same kind of thing), each carrying its own `InfoDetails` **iconOnly in the top right corner** with what that figure measures and what it is worth, then at most two short sentences where a figure means something on its own (Satzenden and Verlauf, the two that need no norm). The figure is the focus on a tile: 1.5rem display type, name above it in small caps, subline below in grey, icon out of the corner. An opened tile takes the whole row via `:has(> .info-details[open])`, since three paragraphs in a 170px column is a word per line. The old layout put a paragraph of method under every figure, which buried the one sentence a reader acts on in six hundred words about measurement; nothing was deleted, only moved. Inside the info block the **limits come first**, because a reader who opens it after seeing a colour is asking what that colour is worth. The German there is plain and dash-free on purpose. `PitchContour.tsx` draws the contour the way phonetics does: semitones relative to the speaker's median, the speaker's own 5-95 band behind it (from `band_low_st`/`band_high_st`, **measured at both ends** — a voice does not reach as far down as up, and the old ±range/2 drew the band on that assumption), one hue, and 6% headroom so an extreme does not sit on the frame. Its horizontal axis is **the user's speaking time, not call time** — the curve holds the user's frames only, so no stretch of it stands for the Persona talking; where one of the user's utterances ends and the next begins there is a light-grey **dashed vertical line** instead of a gap, numbered while the numbers still fit (`intonation.utterance_breaks` → `detail.turn_breaks`, indices into the thinned curve, deduplicated per window). Unvoiced frames are **bridged rather than left as holes** — the earlier hole-per-consonant version broke the line into confetti — but the bridges are dotted and faint and never cross a seam, so the drawing stays continuous without claiming a measurement where there was none (which is the commonest way an F0 plot lies). Two things about resolution, both found by rendering real measurements rather than by reading the code: the curve is stored at **50 ms** (`PITCH_INTERVAL_MS`), not at the loudness curve's 100 ms, because ten samples a second alias a syllable rate of four to five and turn the drawing into a sawtooth; and the component **condenses to one point per unit of plot width** by column median, because two minutes of speaking time is 2400 points across 676 units and the line otherwise grows hair that is rendering noise. `intonation.effective_step_ms` is what the stored `curve_step_ms` and the seam indices are in — thinning works in whole 10 ms frames, so a request for 25 ms yields 20 ms, and the axis was briefly labelling a 19 second contour as 24 seconds. Those last are classified, not just counted (`backend/feedback/interruptions.py`, pure functions over a `Segment` timeline, so they can be recomputed for stored Sessions — the timeline is persisted even though the audio is not): a user start inside a Persona window is a **backchannel** (short and cost the Persona nothing), **terminal** (inside `TERMINAL_WINDOW_MS` = 200, Stivers et al. 2009's turn-taking gap), **hard** (deep, and the reply was actually trimmed) or **soft** (deep but nothing was lost). First rule wins, and the order is the point: counting a backchannel would punish good listening. Two facts about this architecture shape it — a Persona's end is *modelled from dispatched audio* and is **not** shortened by a barge-in, so "did the Persona yield" cannot be read off the timeline and `turn.interrupted` (a real column since migration `e7b3d9c1a542`, not the display marker) is the discriminator; and short backchannels never reach the server at all, since ADR 0036 put a 500 ms VAD floor in the browser. `interruptions` is the hard count, and the drill-down on its tile shows each one as transcript: the Persona's cut-off line, a visible break where the user came in, and **what the Persona had been about to say**, struck through. That last part exists because `turn.unheard_text` (migration `a91c5f70d8e3`) now keeps what had been synthesized but not yet played — deliberately *beside* the transcript and out of the model's history, since ADR 0035 keeps both to the heard words exactly; it is NULL for calls recorded before that, and the block says so. Backchannels are reported beside the count and never against it (they cannot buy an interruption off, which would invent a trade), and the call length and Persona-turn count travel as context. The metric stays a **count**: a rate per Persona turn was built alongside it and dropped again, because at the length these calls actually run (6 to 9 Persona turns) a single interruption already gave 0.11 to 0.17, so every call with one landed on the top step and green was unreachable except at zero — the denominator was saying more than the call was. `persona_turns` travels in the detail as context instead. Each hard interruption also writes a **`Finding`** row, which gives that table its first writer and reader: a Finding is an event that occurred at a moment, not a value judged against a threshold, which is what keeps it inside ADR 0051. `scripts/backfill_interruptions.py` computes all of it for Sessions stored earlier. **The traffic light on `interruptions` (`GREEN_MAX_COUNT` = 0, `YELLOW_MAX_COUNT` = 2) is the other instance of ADR 0078's pattern** — it predates that ADR and was described as an unrecorded exception until F-35 got one too; it meets the seven conditions, and what stays weak about it is not the pattern but the two numbers, which are invented working values with nothing behind them. Confined to the single-call view (never the dashboard, whose no-judgement rule ADR 0065 states outright and which ADR 0078 deliberately did not touch). The light colours **the figure only**, never the whole tile (that would shout an orientation two invented numbers cannot support, and drown out the eight neighbouring Kennzahlen that judge nothing); the step is written out underneath, and the three-step scale it comes from sits on the Kennzahl's own page (`metric_scales` on the detail route, built from the constants so a recalibration reaches the legend too). `metric_scales` is one shape for both readings — `{step, label, range, light}`, `light` null where the scale has no direction — and the German wording travels with it, so the labels live beside the thresholds they describe rather than in a second table in the frontend. Clicking such a tile opens **its own route**, `/trainings/:sessionId/kennzahl/:metricKey` (`SessionMetricView.tsx`), not an in-place panel: the excerpts run several lines each and a reader should be able to link to them and use Back. Easy to remove: the `TrafficLight` class, its two constants, the `metric-light` branch and one CSS block. **Hesitation sounds** are not counted from the transcript: across the stored transcripts not one "äh"/"ähm" survives, because Whisper normalises them away, so a transcript count would measure the recogniser's cleanup. **Lexical fillers** are a different thing — real words that survive transcription — and `fillers` counts them (ADR 0083), with the list per `LanguagePack` (`filler_re`) and the words themselves in the detail. Hesitation sounds are read off the audio instead (ADR 0084; `hesitations`, `backend/feedback/hesitations.py`): a voiced stretch of at least 250 ms whose pitch spans under 2 semitones, on the 10 ms `pitch_per_turn`. An estimate, and said so on the tile — a drawn-out "jaaa" has the same shape — with both constants provisional until checked against recordings. `repetitions` (F-08) counts passages of four or more words said again later, overlapping matches merged so a repeated sentence counts once, and quotes them in the detail. Articulation (F-38, ADR 0084) is **not** measured: the obvious reading, a level drop at word endings, fails on the loudness curve itself, which marks anything 25 dB below the utterance's peak as silence — the swallowed ending is exactly what gets thrown away. `opening` (F-63, ADR 0086, Gesprächseinstieg) checks the user's first turn for a greeting, their own name and a third part that depends on who rang: an **offer of help** on the called side (`offer_re`, "Was kann ich für Sie tun?"), since there the Persona states its own concern, and the **concern** in a reverse (`concern_re`, "Ich rufe an wegen …") — `conversation()` takes `scenario.reverse` for that, and the detail stores whichever key was checked so the tile can name it. It also reads that turn's tempo against the rest of their call. The name is found by its frame ("hier ist", "mein Name ist", "am Apparat"; in English also "I'm") followed by a capital — German has no safe "ich bin", since nouns are capitalised — so a bare name goes unrecognised. The tile therefore shows the three parts marked rather than a count like "1 von 3", which read as a grade, and a screen reader hears "nicht erkannt", never "fehlt". `closing` (F-65, **ADR 0089**, Gesprächsabschluss) is its counterpart at the other end: the user's **last two turns** checked for a recap (`recap_re`, "ich fasse zusammen", "halten wir fest"), a concrete next step (`agreement_re`, "ich schicke Ihnen", "bis Freitag" — deliberately *not* "ich kümmere mich darum", the vague reassurance the Persona's own prompt is warned about) and a farewell (`sign_off_re`, wider than the live path's `farewell_re`, which decides mid-call whether to hang up and is left untouched). Two turns because the recap usually comes one before the goodbye; three would be a third of a call this length. **Absent under three user turns** (`MIN_CLOSING_TURNS`) — the window would reach into the opening, and a call hung up after a sentence has no end of its own. The same parts whoever rang, unlike the opening: ending a call well asks the same of both sides, so a reverse is measured like any other call. `turns_read` rides in the detail so the tile can say where it looked with the backend's own number (ADR 0063's pattern). Both checklist Kennzahlen render from **one list** (`metricParts` in `frontend/src/utils/metrics.ts`), read by the tile, by the progress view's `PartsStrip` and by the PDF — which now names the parts in words there too, instead of printing the bare count ADR 0086 kept off the screen; the bundled fonts carry no check mark, so the recognised parts and the unrecognised ones are two lines. It is the **third metric that can reach backwards** (`scripts/backfill_closing.py [--apply]`): the parts come from words, and the words are stored. `acoustics.py` is the only module that imports `parselmouth`; it measures one Turn's audio inline in the live path (on a worker thread *alongside* the STT round trip, so it costs no latency) and returns raw, concatenable facts (ADR 0047/0048): duration, phonation, pauses, and two curves on one shared 100 ms grid — loudness and, since F-35 was built, pitch. Adding a paraverbal metric is that pattern: a curve on `TurnAcoustics` (no defaults on that dataclass, so every construction has to be revisited), `Turn`/`Conversation` concatenate it, a deriver plus a `MetricDef` in `metrics.py` seeds it automatically. **The audio is never stored (ADR 0048), so a new measurement cannot be backfilled over past trainings** — it starts on the day it ships. `tests/test_acoustics.py` is the one place real Praat runs, against synthetic tones with known answers. `metrics.py` owns the metric inventory, which `provision.py` also seeds, so the two cannot drift — adding a metric is one `MetricDef`. Every metric carries an `aspect` (ADR 0082; `metric_type.aspect`, CHECK-enforced `how`/`what`, ADR 0064's `scenario.category` pattern), assigned in `metrics.py` and seeded with the row: the post-call screen shows one half at a time, switched by the `FilterSlider` the Scenario library uses. Display only, and an unclassified metric falls to `what` rather than out of both halves. `run_length` (**Sprechlänge am Stück**, F-53) is the mean length of runs: phonation time over the number of runs, where a run is bounded by a pause inside an utterance or by the utterance itself, so runs = pauses + utterances (`Conversation.user_turns`, new). It is the **only figure about the speech rather than the silence** — two speakers can match on `pauses` and `phonation_share` and still sound entirely different, two-word bursts against whole sentences — and the only one in the module checked against what listeners hear: Hincks 2005 has it at r = 0.72 against liveliness ratings, *ahead of* the pitch variation quotient's 0.64 that F-35's whole reading rests on. **No step and no colour all the same**: a correlation is not a boundary, nothing published says where a short run stops being conversational, so ADR 0078's first condition is unmet. It is the **second metric that can reach backwards** (after F-51's interruptions, and before ADR 0089's closing) — `scripts/backfill_run_length.py [--apply]`, because everything it divides was already stored by two other metrics (`phonation_share`'s `phonation_ms`, `pauses`' `count`, and a row count on `turn`), so ADR 0048's "a new measurement starts the day it ships" does not bite. The presence of a `phonation_share` row is the backfill's gate, which is the right one: that metric is withheld for the whole call when any Turn's measurement failed. **The figure is not comparable to a published MLR** — 250 ms is Praat's silence threshold, inherited because it already segmented this audio and short by fluency-research standards, so runs come out more numerous and shorter (the first real call: 1.2 s over 27 runs); read it only against the same speaker's other calls, which is all ADR 0051 allows anyway. `phonation_share` (Redefluss, ADR 0085) comes from figures the call already had. It, `pace`, `pauses` and the `loudness` span all rest on `acoustics.py` telling silence from speech at a fixed 25 dB below the peak, which fails over a noise floor — one call recorded over background noise came out 0.6 % silent where every other stored call is 37–67 % — so below 10 % silent frames (`_silence_found`) those four are dropped rather than shown; the pitch-based metrics and talk share are unaffected. An adaptive threshold was considered and rejected: its noise-floor estimate lands in quiet speech on a turn without pauses, and it could not be checked against stored audio, since there is none; `questions` carries its open/closed split in its own `detail`, read off the same question marks so the two always add up. The question words live in the `LanguagePack`, which is why `Conversation` carries the Session's `language_id`. Its metric *keys* are English (`talk_share`, `pace`, `loudness`, …); only their display `name` (e.g. "Redeanteil") stays German, because that is what the UI shows. **No metric carries a target range**: none is validated for this population, and an invented threshold is a score in disguise (ADR 0004/0051), so nothing writes `Finding` rows and the wrap-up prompt forbids judging a figure against a norm. **Nothing in the Feedback is measured against the Persona** either — it is a synthesized voice, so comparing the user to it would report a TTS setting as if it described the user (ADR 0051). `session/models.py` owns the Turn timeline: a Turn is one exchange in memory, but `utterances()` flattens it to one row per speaker for storage, which is what gives every line its own offset and makes the Gesprächsprotokoll timestamped; `conversation()` folds the call for `metrics`. Each speaker's speaking window is tracked separately so the gateway's latency is charged to neither: Reaktionszeit runs from when the Persona stopped speaking, and the Session clock starts at the client's `session.activate`, not at connect. **Storage requires consent (ADR 0066).** `backend/consent.py` is the single place that answers whether a subject's Sessions may be written; `api/session_ws.py::_record` asks it immediately before persisting — at write time, not at the handshake, so a withdrawal *during* a call still takes effect — and it **fails closed**, unlike every other database call in the app, because the alternative is storing data on a guess. The `consent` table is append-only (grant → withdraw → grant is three rows, newest wins) and versioned: bump `CURRENT_VERSION` when the notice changes and every earlier decision goes stale and is asked again. Declining leaves the trainer fully usable — the call runs and the transcript is shown, only storage, wrap-up and history are absent — which is what makes the consent freely given rather than coerced; `SetupView` says so *before* the call. Withdrawing deletes: `backend/deletion.py` removes the subject's Sessions in the same transaction as the decision, leaning on ADR 0026/0052's cascades. **Sessions expire after six months (ADR 0067).** `backend/retention.py` holds the period (`RETENTION`, pinned by a test) and the sweep; `retention_preference` carries a row only for subjects who switched it off, so the *absence* of a row is the default and the period applies to everyone who never touched it. `app.py`'s `_retention_loop` runs the sweep at startup and daily after, driven from Postgres rather than from a scheduled Redis job that would not survive a restart; `scripts/apply_retention.py [--apply]` is the manual path. Switching the sweep back on deletes nothing on the spot, so the control stays a statement about the future rather than a delete button in disguise. The consent log is **not** swept and **not** deleted by any deletion path (ADR 0068): it holds decisions, not their subject matter, and it is the only evidence that the storage which did happen was permitted. Say "your trainings are deleted", not "all your data". Alongside it: `GET /api/me/data` (counts and period — the *extent* of what is held), `GET /api/me/export` (every row the subject owns, nested JSON, served as a download so a page of transcripts is not left in a tab) and `DELETE /api/sessions/{extern_id}` for one training, which 404s for an id that is absent *or* not the caller's, exactly as the read route does. **Spoken content no longer goes into the log by default**: `clients/stt.py` logs the transcript's *length* (which still catches an empty transcript or Whisper's near-silence hallucination) and the text itself only under `LOG_TRANSCRIPTS`, off unless set and announced with a boot warning while on — that log is outside every deletion path, so it is a default and not a guarantee. Backups are not reached because **there are none** — no backup service in `compose.yaml`, no `pg_dump` in the repository, Postgres on a Docker volume. Whoever introduces backups has to add a retention policy to ADR 0066 in the same change, or a deletion that is complete today quietly stops being so. `persistence.py` writes it all in one transaction after the call has ended, never during it (ADR 0034) — a Session the client abandoned mid-call is deliberately not persisted, and a database failure is logged but never fatal, since the Transcript is already in memory and gets sent either way. `generator.py` produces the wrap-up in the RQ worker (ADR 0049), and `GET /api/sessions/{extern_id}` (ADR 0050, behind the same bearer token as the rest of `/api`, and only for the caller's own Sessions: the route compares `session.subject_id` with the token's `sub`, and someone else's `extern_id` answers 404 exactly like an unknown one, because a 403 would confirm the id exists — ADR 0031/0050) serves it to the post-call screen, which polls (`useSessionFeedback`, `FeedbackView`). The wait for it has a screen of its own (`FeedbackWaiting`, the `analysing` screen in `App.tsx`): the waveform of the call being read by a magnifier passing over it, one rotating line saying what is being counted, and a quiet way past it to the Transcript — which may be the only copy (F-64), so the screen is never a lock. It runs its own poll and hands over the moment the wrap-up settles, or after two minutes regardless (`useSessionFeedback` waits ten, which is the right patience for a block on a page and the wrong one for a screen holding nothing else). It is skipped entirely where no Session was stored: no consent, no wrap-up on the way (ADR 0066), and a wait for something that is not coming is the one thing it must not be. Unlike the die (F-62) and the card turn (F-61) it is still shown under `prefers-reduced-motion`, standing still — there is nothing behind it to skip to. That wrap-up carries **six** fields, not three: alongside the summary and the two point lists, F-42's `phase_language` paragraph says whether the register moved with the phase of the call (warm → sachlich → warm across Opening, Core Business, Closing), and `feedback.tone_fit` (**ADR 0079**, migration `b6e2d914f70a`) says whether the way the trainee sounded suited **the occasion of this call** — one LLM call for all six — the sixth being `pressure_turns` (**ADR 0081**, migration `f3a5c81be47d`), the only one nobody reads: the ids of the Persona utterances that put the trainee under pressure, which decide the stretches the segment measurements are computed over. **F-62's "Souveränität unter Druck" is measured from them** — the same five Kennzahlen that stay defined on part of a call (`talk_share`, `pace`, `pauses`, `run_length`, `loudness`; `reaction_time` would describe the boundary, the counts shrink with the stretch, the Sprachmelodie needs more voiced speech than a stretch holds) computed once over the marked exchanges and once over the rest, and stored as `measurement.segment` in (`call`/`pressure`/`rest`). `backend/feedback/segments.py` writes no derivation of its own: a segment is a **slice of the same call**, so `conversation()` folds it as it folds the whole and `metrics.py` runs unchanged. A marked line puts the utterance that *answers* it into the pressing stretch (the causal direction, pinned by a test — off by one here measures the wrong sentences while looking healthy); a user id or a foreign one is dropped like a bad `turn_id`; under three user utterances a stretch is not measured; the whole-call rows are never rewritten, and `_store_segments` sits behind its own failure boundary and is idempotent for `requeue_feedback.py`. **Nothing compares the two figures** — no difference, no index, no colour, no word like "stable" — because how large a gap means something is exactly the norm ADR 0051 refuses; the interface puts them side by side and says twice that the split was a model's judgement and the figures beside it a measurement. This needed the *first* per-utterance numbers in the schema, `turn.acoustics_json` (speaking time, phonation, pauses, its stretch of the loudness curve): the audio is gone when the call ends (ADR 0048) while the split is decided minutes later by the worker, so ADR 0081 takes a narrow exception to ADR 0051 — **raw facts, never statistics, never shown** — and in exchange a later change to how a call is divided can reach Sessions already stored. Stored Sessions from before it gain nothing and never will; the interface says so rather than showing an empty block. `tone_fit` closes the gap every F-35 caveat kept naming: how much melody is appropriate depends on the occasion, the application knew the occasion the whole time (the picked Scenario) and never said anything about it. Prose for ADR 0056's reasons, and a per-Scenario norm would be ADR 0051's refused invention four times over. It is why `_dossier` now opens with the played Scenario's `description` and `call_goal` — the wrap-up used to see only transcript and statistics, so the situation had to be *inferred*, and this judgement may not rest on an inference; `success_condition` is deliberately withheld, being a result rather than an occasion and an invitation to grade the outcome under the heading of tone. Three prompt rules keep it a description: **start from the occasion, not from the figures** (the other way round the model reads a figure, calls it lively and works out afterwards what call it must have been), **there is no correct register for a kind of call**, and **a tone that fitted is a normal answer — do not manufacture a mismatch**. Rendered **on the Sprachmelodie page and not in the wrap-up** (`IntonationReading`'s `toneFit` prop, from `detail.feedback.tone_fit`), directly under the classification whose caveat it resolves, on its own ground with a line saying it was written by the model and is a reading rather than a measurement. Both second-level pages end in `GoalStatements.tsx`: every sentence the wrap-ups wrote about that goal, **quoted, never summarised**, each labelled Stärke/Verbesserung in words (colour would grade the call) and linking into the training it came from. A Kennzahl shows the goals it is the *first* metric for (`focusMetrics.goalsForMetric`), or Reaktionszeit would collect the statements of three goals it is only a supporting figure for. A focus tile's one drill-down is the goal's own page, and the activity goals have none, since what answers them is the two charts at the top of the same screen. It runs at the app's full width (`app-page-wide`, 1440px, with `AppLayout wide` widening the header to match so the two align) and adds **no endpoint** — `GET /api/sessions` already carries each Session's Measurements, and an aggregate route would be a second path to the same numbers; two charts carry the screen while little has been measured, both needing only the session rows: `ActivityCalendar.tsx` (a **calendar** of the training days — the count in the cell, a three-step shade of the activity hue behind it, the day's date where nothing happened, a ring on today; it replaced a bar per day/week/month, which held the same numbers and none of the shape of a week, and the ramp is validated as an ordinal one: monotone lightness, light end 2.23:1 on a white card. **One month at a time, opening on the current one**, paged with two arrows back to the month of the oldest training; six months as small multiples made the card a wall of grids and half a metre taller than the block beside it. It counts **completed trainings only** — an abandoned call is neither counted nor marked, since the question is when somebody trained. It is also the one block the **period switch deliberately does not reach**: that switch says which trainings the Kennzahlen are read over, and a calendar carries its own range in the grid, so cutting months off it would state the same thing twice as a hole in a chart. It therefore reads every stored Session, and since the switch was moved *under* the block (below), so do the three counted figures and the variety grid beside it — a part of the block above the switch that still followed it would be exactly the ambiguity the move removed. That grid orders its rows and columns most played first and shows five Scenarios before a "N weitere Szenarien anzeigen" button (`VarietyGrid.COLLAPSED_ROWS`, the `.session-more` style the history and the library share). The columns are sized to the calendar (`minmax(260px, 340px)` against `1fr`) rather than split 3:2: one month of seven columns has a natural width, and the larger share only stretched the card while the variety table ran out of room) and `VarietyGrid.tsx` (Scenario × Persona, *played combinations only* — a full-library grid with empty cells would turn a description into a homework list), plus call length as a derived series beside the measured ones; **Colour on this screen is identity and never judgement** (`utils/metricGroups.ts`): one hue per *family* of Kennzahlen — Sprechweise, Gesprächsinhalt, Aktivität — held by two structural rules rather than by care. The module that assigns a hue never sees a value, so a number cannot move a colour (which is exactly what a traffic light does); and red, amber and green are excluded, because ADR 0078 already spent those three on the single-call traffic light and a hue that means something there must not carry identity here. Three hues and not ten: slots 1, 5 and 7 of the documented categorical palette, validated as an all-pairs set against a white card (CVD ΔE 13.0 against a target of 8, normal-vision 16.3 against a floor of 15) — a hue per metric would be eight, where adjacent pairs stop being separable. The Kennzahlen are **a sparkline table, one row each** (`ProgressMetricTable.tsx`: name, last value, course, own usual range, number of trainings), grouped under the two `metric_type.aspect` families as row groups with a heading in the family's hue (which is why `aspect` rides on the listing as well as the detail route). It replaced a tile grid behind a `FilterSlider`: that switch was sized for nine Kennzahlen, the inventory grew to sixteen, the halves were nine and seven tiles, and the wall it was built against was back — a table fits all of them on one screen and is the better accessible form besides. Counts (unit `Anzahl`: `questions`, `fillers`, `repetitions`, `hesitations`, `interruptions`) are shown as **whole numbers per call**, and their usual range rounded and clamped at zero (`progressStats.isCount`/`formatBand`) — a per-100-words version was built and taken out again at the user's request, because it turned every count into a decimal; the Gesprächsdauer row is the context for a long call's higher count. `word_count` itself is left out of the overview (`OVERVIEW_HIDDEN`), since across trainings it repeats the call length, but stays reachable from its page and from "Prägnante Sprache". **`loudness` is left out of every cross-call view** (`progressStats.NOT_ACROSS_CALLS`, applied in `toSeries` and in `segmentStats.segmentTrainings`): its dB span is the recording's level, so across calls it measures the microphone and the distance as much as the speaker — the argument that retired the loudness focus goal. The single call's page keeps its curve and its pressure/rest pair, where the device is the same on both sides. `opening` has a series shape of its own (`SeriesShape` `"parts"`): no line and no band, because a course of 1-3-2-3 over a band reads as a score climbing to full marks — exactly what ADR 0086 kept off the single call's tile — but one mark per training with the count of recognised parts (`PartsStrip.tsx`) and "in X von N Trainings alle 3 Teile erkannt". The page reads top to bottom as **"Ihr Training"** (the three counted figures as cards, the calendar and the variety grid, all over every stored training) → **a rule carrying the period switch** → focus goals → **what recurs, with the practice suggestion as a full-width band under the two lists** (a third card in their row ran three times their height, holding a paragraph, an offer and a button where they hold two lines each; it still follows directly from the improvements beside it, which is the adjacency that mattered) → the Kennzahlen table. The switch stands where its reach begins, so the page says by placement what it used to need a comment for: everything above it counts every training, everything below reads the selection. The one block that leads back into training stays high rather than last on the longest page. The section headings are the wrap-up's own (`SectionHeading.tsx`, eyebrow plus title, moved out of `FeedbackView.tsx` for the purpose), so the page over many trainings and the page over one look like the same application. The switch selects **the last 5, the last 10 or all trainings** (`progressStats.latest`), not 30 days / 6 months / Gesamt — the retention limit made the last two the same, and a day window was empty for anybody training in bursts. Explanations sit behind `InfoDetails` like everywhere else in the app, with the one sentence a reader must not miss kept in view (the page lead's "Bewertet wird hier nichts", "Gezählt wird, was Ihre Auswertungen geschrieben haben", "…ist kein Ziel" under the table). A focus tile shows the goal's first Kennzahl as before and **up to two further ones** as small lines under it (`SupportingMetrics`), because for Sprechtempo or Aktives Zuhören the goal *is* the combination; a goal with no measurement shows its mentions as **pips**, the recurring block's marks (`MentionTally.tsx`), instead of a large "3 von 8" that read as a mark. The charts on the focus tiles and the detail level carry a hover layer that *adds* to the text alternative and never replaces it — the `aria-label` still holds the numbers and the detail level still repeats them as a table, so nothing is hover-only. `utils/progressStats.ts` does the grouping, the own-median-plus-MAD band (the same construction `metrics.py` uses for the loudness course, and the only reference point ADR 0051 allows) and the `MIN_SESSIONS_FOR_SERIES` = 3 rule that shows single values instead of a two-point line. Focus goals (F-62) drive the top block: `utils/focusMetrics.ts` maps each goal to the Kennzahlen behind it, and a goal with none says so rather than rendering an empty tile — 8 of the 14 carry a measured series today (the Gesprächsabschluss since ADR 0089), **1 (Souveränität unter Druck) a comparison of two stretches rather than a series** (`kind: "segment"`, ADR 0081: a line through it would be the difference over time, which is the one number that goal must not have, and across calls it would average pressures that were different things), 2 are answered by activity figures, and 3 only by wrap-up text. No focus goals means that block is *replaced* by the three most-varying metrics plus an invitation, never left empty. The recurring block is **real since ADR 0080** (`ProgressRecurring.tsx`, `utils/goalMentions.ts`): `feedback_point.focus_goal_id` (migration `d4c81b70e2a5`) records which of F-62's fourteen goals a point is about, assigned by the wrap-up in the call it already makes, so the screen can count what the wrap-ups *said*. **A frequency of statements, never a measurement** — "in 4 von 8 Auswertungen genannt", counted **per training and not per point**, denominator = trainings whose wrap-up carries any tag (one with none never had an opinion), a theme from **2 mentions**, at most 3 per column. Invalid keys become NULL at the write boundary (`generator._goal_ids`) rather than raising, and the two habit goals are refused there as well as in the prompt. The tags ride on `GET /api/sessions` as `feedback_goals` — `{kind, goal, text}` since **ADR 0064's amendment**, which narrows "no wrap-up text on the listing" to the *tagged points*: the second level has to show what was written about a goal and not only how often, and for the goals with no measurement the sentences are all there is, so a count nobody can read behind reads as a measurement. The summary, the phase paragraph, `tone_fit` and every untagged point stay on the detail route; the listing eager-loads the points and their goal, which it had not, so a page is a fixed number of queries. The view still adds **no endpoint**. Side effect that justified the whole change: the goals with no measurement of their own — at the time Einwandbehandlung, Abschluss, Empathie and Artikulation, the Abschluss having gained one since (ADR 0089) — finally have a data basis, and for Empathie and Artikulation it is the only one they will ever have. `ProgressPreview.tsx` is deleted; where nothing can be counted yet the block says which of the three reasons applies. **Block E is built too** (`ProgressPractice.tsx`, `utils/practiceRoutes.ts`): the most-named improvement goal becomes **one** suggestion with a Starten button, by three routes in order — the *Folgeszenario* written from the very training where the point was last named, else a Scenario of the kind that goal is practised in (editorial table, unplayed preferred), else any unplayed Scenario for the goals that bind to no kind of call. It always names its ground first ("weil X in 3 Ihrer Auswertungen genannt wurde"), because a suggestion without one is an instruction. The **Persona is the one from that same training**, not chosen: the wire carries no difficulty on a Persona, so the concept's "fordernde Persona" is unpickable, and holding the voice constant makes the next call an exercise on the point. A goal missing from the editorial table yields **no** suggestion, so adding a catalogue goal forces a decision. Hands over through `TrainingStart` like the history does. Building it surfaced an old defect: `metric_type` still held the pre-ADR-0057 German keys *active* beside their English replacements (same display name, so a renamed metric would have drawn two identical charts) because `provision.py` never applied `_deactivate_missing` to MetricType although ADR 0057 says it does. Fixed there, plus `active` on the listing's measurements so the dashboard drops retired ones; the *detail* route deliberately does not filter, since a past Session should show what was measured then. Merging old and new keys was rejected: ADR 0051 changed the definitions, and splicing two different measurements into one line is the quiet kind of wrong. Self-service deletion **is** built (ADR 0066): withdrawing consent removes everything, `DELETE /api/sessions/{extern_id}` removes one training, and both go through `backend/deletion.py`. Because `session_scope()` is synchronous, database calls from the async Session path go through `asyncio.to_thread`, and FastAPI's sync `def` endpoints get the same effect from its threadpool; nothing blocking may run on the event loop that streams live audio.

## Build / Run

- Frontend: `cd frontend && npm install && npm run build` (writes to `frontend/dist`, which the backend serves). The Vite dev server (`npm run dev`) is not a supported workflow — it has no backend URL configured (there is no `VITE_API_URL` anymore; the app is always run via Docker) and VAD is broken under it anyway (see next bullet). CORS in `backend/app.py` still allows `http://localhost:5173` but nothing depends on it.
- Turn-taking uses Silero VAD in-browser (`@ricky0123/vad-web` + `onnxruntime-web`, ONNX+WASM); `npm run dev`/`npm run build`'s `predev`/`prebuild` hooks (`frontend/scripts/copy-vad-assets.mjs`) copy its ~15MB of runtime assets into `frontend/public/vad/` (gitignored, regenerated on every dev/build run — not tied to `npm install`, since the Docker build's `npm ci` layer runs before the rest of the source, including this script, is even copied into the image). Known gap: this currently fails under `npm run dev` specifically — Vite 5's dev-server import-analysis 500s on onnxruntime-web's dynamically-imported `.mjs` WASM glue (a dev-only Vite/onnxruntime-web interaction, unresolved so far). The production build (`npm run build`, served by the backend) is unaffected — use that path when testing VAD/turn-taking changes.
- Local backend: `uvicorn backend.app:app --reload`
- Docker: `docker compose up --build` (builds the frontend too, via a multi-stage Dockerfile; serves on `http://localhost:8391` — a deliberately non-standard host port, mapped to the container's 8000, set in `compose.yaml`). Add `--watch` to pick up code changes automatically (`develop.watch` in `compose.yaml`): backend edits are synced into the running container and the app restarted, without a full rebuild; frontend edits and `requirements.txt` changes trigger a rebuild instead. To restart from scratch: `docker compose down` → `docker compose build` (add `--no-cache` if a frontend change is not showing up) → `docker compose up`. Postgres and the Keycloak session survive that. To re-import `keycloak/direkt-realm.json`, also drop the Keycloak volume first (`docker volume rm direkt-calltrainer-keycloak-data`) — Keycloak then mints fresh signing keys, invalidating the browser session, but `apiFetch` catches the resulting 401 and redirects to login. `docker compose down -v` wipes Postgres too. The Python base image is **pinned to 3.12**, not `python:3-slim`: that floating tag had already moved to 3.14, where SQLAlchemy 2.0.36 cannot resolve the `Mapped[int | None]` annotations and every database import dies.
- `LOG_TRANSCRIPTS` (in `.env`, default off) writes the spoken content of every call into the log file. Leave it off outside local debugging — no deletion path reaches that file (ADR 0066), so a transcript written there outlives a withdrawn consent and a deleted training. The app logs a warning at boot while it is on.
- Copy `.env.example` to `.env` and fill in real values before running — `.env` is gitignored and read via `env_file` in the compose file, and by Vite (`envDir` at the repo root) for the `VITE_OIDC_*` build vars.
- Keycloak (ADR 0009): `docker compose up` starts a local Keycloak on `http://localhost:18081` and imports `keycloak/direkt-realm.json` (client `calltrainer-frontend`, dev users `niklas`/`mathias`/`eberhard`, password = username). Each dev user carries a `tenant` attribute (`niklas`/`mathias` → `solox`, `eberhard` → `appollo`) that the `calltrainer tenant` protocol mapper puts in the token, so they resolve to those tenants (ADR 0060). The realm's user profile sets `unmanagedAttributePolicy: ENABLED` so that custom `tenant` attribute survives import. Each dev user's `id` is pinned in the JSON, so a re-import keeps the same `sub` and authored Scenarios (`scenario.created_by`, ADR 0058) are not orphaned — Keycloak's realm JSON rejects unknown keys, so that rationale lives here, not in a comment field. Edit the JSON → wipe the volume to re-import: `docker compose down -v` (or `docker volume rm direkt-calltrainer-keycloak-data`). `KC_HOSTNAME` pins the token issuer to `localhost:18081`; the app container reaches the realm's keys over the compose network via `OIDC_JWKS_URL` (`backend/auth.py`). Keycloak admin console: `admin`/`admin`. For a host-only `uvicorn` run, point `OIDC_ISSUER` at the same URL and drop `OIDC_JWKS_URL` (the host can reach `localhost:18081` directly).
- There is no LLM mock any more — `scripts/mock_llm_server.py` was removed in commit 113394f and never replaced, so anything touching STT/LLM/TTS needs a reachable `DIREKT_URL`. To exercise the wrap-up generator without one, stub `backend.clients.llm.complete`.
- Checking the pipeline backends: `python scripts/check_backends.py` fires one minimal real request at each configured STT/LLM/TTS backend and logs OK/FAIL per step (exit 0 only if all pass); it respects the `SKIP_KUGELAUDIO` toggle (forces the TTS check onto the DiReKT fallback instead of KugelAudio). The app runs the same check (`backend/clients/health.py:check_backends`) at startup from the `lifespan` handler — a dead model is logged as `Startup check: <STEP> FAILED` but does not stop the app from booting.
- Every compose service carries `restart: unless-stopped`. Without it a Docker restart or a crash leaves a container down, and on the **worker** that is silent — calls keep working and wrap-ups simply never appear, which is exactly how a dead worker went unnoticed for hours. Note also that `docker compose up -d app` does *not* start the worker (it is not in app's `depends_on`); use a bare `docker compose up -d`. If wrap-ups are missing, `docker compose ps -a` first.
- Retention: `python scripts/apply_retention.py` lists what is past the six-month period, `--apply` deletes it. Works from a host shell (no Redis needed). The app sweeps daily by itself; this is for checking the period before it bites or clearing a backlog after downtime.
- `python scripts/inspect_pressure_segments.py [--session <extern_id>] [--transcript]` reads back how the wrap-up split each stored call into demanding stretches and the rest (ADR 0081). Read-only, host shell, no model and no Redis. It exists because the one thing about that feature no test can answer is whether the *marks* are any good: a run where every Persona line is marked, or none across a dozen calls, means the two stretches are not two, and the screen looks entirely healthy either way. The `Befund` column separates `none-pressing` (judged, nothing pushed) from `unjudged` (the model dropped the key) and `no-facts` (recorded before ADR 0081, so nothing can ever be measured for it).
- `python scripts/backfill_closing.py [--apply]` computes F-65's Gesprächsabschluss (ADR 0089) for Sessions stored before it existed. Host shell, no Redis and no model, idempotent, and it skips a Session with fewer than three user utterances exactly as the live path does. Possible because the three parts are read from the stored transcript alone.
- `python scripts/backfill_run_length.py [--apply]` computes F-53's Sprechlänge am Stück for Sessions stored before it existed. Works from a host shell (no Redis, no model), idempotent, skips Sessions that already carry the figure. Possible because it divides only figures two other metrics already stored — see the metric's note above; the audio is long gone (ADR 0048).
- Wrap-ups can be regenerated: `docker compose exec app python scripts/requeue_feedback.py [--apply]` re-queues every stored Session that has Turns but no Feedback. Nothing is regenerated from audio — the wrap-up is written from the stored Transcript and Measurements (ADR 0049), so a Session from days ago can still be analysed. The job writes the wrap-up and nothing else since ADR 0069's amendment — the Folgeszenario is asked for from its own route, so re-queueing never produces one. Must run inside the container: Redis is not published to the host.
- Feedback worker: `docker compose up` now also starts `redis` and a `worker` service running `python -m backend.worker`. The worker shares the app's image and database but no request cycle; if it is down, calls still work and wrap-ups simply queue. RQ forks per job, so the worker only runs on Linux — use the container, not a host process, on Windows.
- Database: the app migrates to head and seeds the reference tables itself at startup (`backend/db/provision.py`, called from the `lifespan` handler), so `docker compose up` needs no manual step — a provisioning failure is logged as `Database provisioning failed` and does not stop the app, but the setup endpoints then serve nothing and every Session fails to persist. To do it by hand against a host-side database, `docker compose up -d db` then `python scripts/seed_reference_data.py`, which is a thin CLI over the same `provision()`. The seed script calls `load_dotenv()` itself; `backend/db/session.py` does not — it assembles the connection URL in `build_database_url()` lazily, on the first call to `session_scope()`/`get_engine()`, so importing it never requires an environment. There is **no `DATABASE_URL`**: the URL is built from `POSTGRES_USER`/`POSTGRES_PASSWORD`/`POSTGRES_DB` plus an optional `POSTGRES_HOST`/`POSTGRES_PORT`, which default to `localhost:5432` for host-side calls — one place for the password instead of a URL duplicated across `.env` and `compose.yaml`. Alembic uses the same function, so migrations can never run against a different database than the app; the app and worker containers get `POSTGRES_HOST=db` from `compose.yaml`, which is the only part that differs. Provisioning takes a Postgres advisory lock (`PROVISION_LOCK_KEY` and the `advisory_lock()` context manager in `backend/db/session.py`) twice in sequence, never nested: once in `migrations/env.py` around the migration and once in `provision.py` around the seeding, each on a connection of its own. That is what keeps the app and the worker starting at once from applying the same revision twice *and* from racing `_upsert` into a duplicate-key rollback that would log as `Database provisioning failed`. Do not hold it across both steps — the process would wait on itself, without a timeout.
- Schema changes: edit `backend/db/models.py`, then `alembic revision --autogenerate -m "..."`. Constraint and index names come from the naming convention on `Base.metadata` (`backend/db/base.py`, ADR 0053) — never name one by hand, and never remove the convention: without it autogenerate emits unnamed constraints whose `downgrade()` cannot run. Note that `op.create_check_constraint`/`op.drop_constraint` apply that convention *themselves*, so a migration passes the bare name (`status_valid`), never the prefixed one. Every foreign-key column carries `index=True` (ADR 0052); two tests enforce both rules. Alembic does **not** autodetect `CHECK` constraints — those have to be written into the migration by hand. **Always read the generated migration before applying it** — autogenerate adds `NOT NULL` columns without backfilling, which fails on non-empty tables, and it cannot recognise a rename: it emits a drop plus a create, which would destroy stored Sessions. The ER diagram is regenerated automatically on every docs build (see below); `python scripts/generate_erd.py` refreshes `docs/er_modell.png`/`.svg` on demand and needs the Graphviz `dot` binary (`brew install graphviz`). Three invariants the database enforces since migration `a7c39e5f21b8`, to be kept in `models.py` and in any migration that touches these tables: `measurement` is unique per (`session_id`, `metric_type_id`, `segment`) since ADR 0081 (it was the first two until then) and `turn` per (`session_id`, `seq_index`) — one set of statistics per Session *per stretch of call*, and a transcript order that does not depend on the server. `segment` is NOT NULL with a real value (`call`) for the whole call rather than a nullable column, because Postgres treats two NULLs as distinct and the whole-call rows would drop out of the constraint that exists to protect them; foreign keys into the reference tables (`persona`, `scenario`, `language`, `metric_type`) carry **no** `ondelete` at all, the nullable ones included — only back-references into rows the Session owns (`feedback_point.turn_id`/`finding_id`) are `SET NULL`; and every timestamp column is `DateTime(timezone=True)` and written exclusively with `datetime.now(UTC)`, never a naive `datetime.now()`, because Postgres would read a naive value in the server's zone and every stored time would shift if the app container's `TZ` ever differed. Column defaults (`active`, `attempts`, `extern_id`) are Python-side only, no `server_default`, so a row inserted from `psql` has to name them.
- Docs site (arc42 + ADRs): `mkdocs serve` (serves on `http://localhost:8000`; the app is on `8391` now, so no clash). `mkdocs build` writes static output to `site/` (gitignored).

- Tests: `pip install -r requirements.txt` then `pytest` (config in `pytest.ini`, suite in `tests/`). Feature-traceable backend tests — every file cites the `F-xx`/`R-xx`/ADR it proves; see `tests/README.md` for the traceability matrix. Two kinds live side by side. Most need no network, database, credentials or browser: the STT/LLM/TTS pipeline backends are faked in `tests/conftest.py`, the REST layer runs over an in-process ASGI transport, and `conftest.py` claims the `POSTGRES_*` names with deliberately unusable values *before* the backend is imported, so a test that does not ask for a database cannot reach the real one by accident — `backend/clients/config.py` calls `load_dotenv()` on import, which would otherwise put the developer's real settings into the environment for the whole session. `tests/test_database_isolation.py` guards that ordering. The persistence tests each create their own throwaway database on the server from `.env`, migrate it and drop it afterwards — so Postgres has to be running (`docker compose up -d db`), but the development database is never touched; without a reachable server they skip rather than fail. They cover the migration chain in both directions, the naming convention and the FK indexes, seed idempotency and deactivation (and that a deactivated row leaves the setup endpoints), the Session write path, the setup and session endpoints including the ownership check, the wrap-up job's status lifecycle, the unique and undeletable invariants above, and that deleting a Session removes its subtree by ORM and by raw SQL while leaving reference data alone.
- Frontend tests: `cd frontend && npm test` (Vitest, `vitest run`). Deliberately narrow — not a general component-test setup. It covers only the live-call audio path: the barge-in races in `useStreamedAudioPlayback` and `useSessionSocket`, which `tsc` cannot see and which are near-impossible to catch by hand. jsdom plus hand-written Web Audio / WebSocket fakes (`frontend/src/test/setup.ts`) that let a test drive decode timing and socket delivery frame by frame; no network, no browser. The specs are excluded from the production build's type-check (`tsconfig.json`), so they are checked only by esbuild when they run.
- Lint: `flake8 .` and `PYTHONPATH=. pylint backend/ scripts/ tests/`. Both are clean (pylint 10.00) and should stay that way — a deliberate exception carries an inline `# pylint: disable=X  # reason`. `PYTHONPATH=.` is required — without it pylint cannot resolve the `backend.*` imports and reports nothing but import errors. Alembic revisions are excluded from both (their formatting comes from autogenerate and would be rewritten on every new revision) — via `ignore-paths`/`per-file-ignores` patterns written to match even when an editor lints one by its absolute path. **`duplicate-code` (R0801) is switched off per file, in fourteen of them, each saying why** — do not remove those lines as dead weight and do not replace them with a global disable or a raised `min-similarity-lines` (it sits at 4): the three real duplicates were merged instead, and a threshold high enough to silence what is left would have swallowed those too. The three kinds of exception: test modules repeat fixture data on purpose, so a failing test shows what it ran against; `api/account.py` and `api/sessions.py` each hold a `_feedback` that only looks like the other's, the export serving `created_at` and plain points where the detail route serves `turn_id` and the focus goal; and the backfill scripts, having handed their command line to `scripts/_backfill_cli.py`, still each own the `main()` and `if __name__` guard no script can share. What *was* merged: `interruptions.finding_description` (the live path and the backfill built the same German sentence twice, so a rewording would have applied to new Sessions only), `api/_loading.py::SESSION_SUBTREE` (two eager-load lists that would have drifted into N+1 queries), and that shared backfill CLI.
