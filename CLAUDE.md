# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Calltrainer is an AI-powered phone conversation trainer that provides real-time analysis and behavioral feedback during simulated calls (from README.md).

## Current State

FastAPI backend (`backend/app.py`) serves the API and, once built, the React + TypeScript frontend (`frontend/`, built with Vite; the backend serves `frontend/dist`). `/health` is a plain health check; `/api/personas` and `/api/scenarios` list the Persona/Scenario options shown before a Session starts — any Persona can run any Scenario, no compatibility to filter by. Auth is Keycloak/OIDC (ADR 0009, now built): the SPA logs in with PKCE against the `direkt` realm (`calltrainer-frontend` client), `backend/auth.py` verifies the bearer JWT (`OIDC_ISSUER`, audience `calltrainer`) on `/api/personas`, `/api/scenarios` and the `/ws/session` handshake — the WebSocket carries the token in its `session.start` message since a browser can't set a header on it. `/health` and the static frontend stay open. No role checks. `docker compose up` brings its own Keycloak on `:18081` (`keycloak/direkt-realm.json`, dev users alice/bob/carol). There is no Language selection: each Persona has exactly one fixed Language/voice, carried by its database row (ADR 0041) and seeded from `backend/db/seed_data.py`. German and English are both supported, per Persona — the language decides which `LanguagePack` (`backend/session/language_packs.py`) supplies the closing-intent patterns, the opening examples and the fallback closing line, so adding a language means adding a pack and a Persona that names it, never a global setting. The live Session itself runs over a per-Session WebSocket at `/ws/session` (`backend/api/session_ws.py`): the client streams one full Turn of recorded audio at a time (browser-side voice-activity detection ends each Turn automatically, no manual button) and the user can talk over the persona to cut a reply short (barge-in, ADR 0035); the server runs each Turn through STT → streamed dialogue generation → chunked TTS (`backend/session/orchestrator.py`, `backend/clients/`), and streams synthesized audio back chunk-by-chunk so playback can start before the full reply is done generating (ADR 0033, which supersedes the earlier non-streaming pipeline; ADR 0044 refines the TTS leg — each chunk is forwarded to the client sub-chunk by sub-chunk as KugelAudio's `stream_async` produces it, not buffered). STT and LLM call the same OpenAI-compatible DiReKT model gateway, configured via a single `.env` base URL/key pair (`DIREKT_URL`, `DIREKT_API_KEY`) plus one model name per step (`STT_MODEL`, `LLM_MODEL`) — neither has a fallback. TTS defaults to KugelAudio (a separate SDK, not an HTTP endpoint on the DiReKT gateway; `KUGELAUDIO_API_KEY`/`KUGELAUDIO_MODEL`), falling back to the DiReKT TTS model (`TTS_MODEL`) if KugelAudio fails, or always if `DEBUG=True` is set (`backend/clients/config.py`). No text is shown during the live call, only a state animation (listening/thinking/speaking) — the full Transcript is sent once, at the end, and shown as a post-call summary. Persistence lives in `backend/db/`: `models.py` holds the SQLAlchemy schema, `session.py` the `session_scope()` context manager used for all database access, `migrations/` the Alembic revisions, and `provision.py` the migrate-and-seed step the app runs at startup. Postgres runs as the `db` service in `compose.yaml` (ADR 0010). The migrations and the ER diagram in `docs/datenmodell.md` are generated from `models.py`, not edited by hand; the schema's rationale is in ADRs 0025 through 0032 and 0050. The backend test suite lives in `tests/` (pytest, feature-traceable, faked pipeline — see the Tests section under Build / Run); the frontend has no JS test runner. `docs/arc42.md` is filled in.
Post-call analysis lives in `backend/feedback/` and produces **one set of statistics per Session, never per Turn** (ADR 0051): F-53's Kennzahlen — Redeanteil, Fragen, Sprechtempo, Wortanzahl, Reaktionszeit, Sprechpausen — plus F-37's loudness curve. `acoustics.py` is the only module that imports `parselmouth`; it measures one Turn's audio inline in the live path and returns raw, concatenable facts (ADR 0047/0048). `metrics.py` owns the metric inventory, which `provision.py` also seeds, so the two cannot drift — adding a metric is one `MetricDef`. **No metric carries a target range**: none is validated for this population, and an invented threshold is a score in disguise (ADR 0004/0051), so nothing writes `Befund` rows and the wrap-up prompt forbids judging a figure against a norm. **Nothing in the Feedback is measured against the Persona** either — it is a synthesized voice, so comparing the user to it would report a TTS setting as if it described the user (ADR 0051). `session/models.py` owns the Turn timeline — `utterances()` is the single source of speaking order (both the WebSocket Transcript and the persisted Turn rows come from it), `conversation()` folds the call for `metrics`. Each speaker's speaking window is tracked separately so the gateway's latency is charged to neither: Reaktionszeit runs from when the Persona stopped speaking, and the Session clock starts at the client's `session.activate`, not at connect. `persistence.py` writes it all in one transaction (ADR 0034), `generator.py` produces the wrap-up in the RQ worker (ADR 0049), and `GET /api/sessions/{oeffentliche_id}` (ADR 0050, behind the same bearer token as the rest of `/api`) serves it to the post-call screen, which polls (`useSessionFeedback`, `FeedbackView`). The Session row is written under the caller's Keycloak `sub` (ADR 0009/0031), handed to `persist_session` straight from the handshake. `Messung`/`Befund` hang off the `Session`; a `Turn` row keeps transcript and offsets, which is what makes the Gesprächsprotokoll timestamped. `Befund` has no writer and no reader — the table stays for pilot data, but nothing in the API, the prompt or the frontend refers to it. There is no Session history and no shareable route — the wrap-up is reachable for as long as that screen is, plus a `sessionStorage` entry so a reload does not discard it.

## Build / Run

- Frontend: `cd frontend && npm install && npm run build` (writes to `frontend/dist`, which the backend serves). The Vite dev server (`npm run dev`) is not a supported workflow — it has no backend URL configured (there is no `VITE_API_URL` anymore; the app is always run via Docker) and VAD is broken under it anyway (see next bullet). CORS in `backend/app.py` still allows `http://localhost:5173` but nothing depends on it.
- Turn-taking uses Silero VAD in-browser (`@ricky0123/vad-web` + `onnxruntime-web`, ONNX+WASM); `npm run dev`/`npm run build`'s `predev`/`prebuild` hooks (`frontend/scripts/copy-vad-assets.mjs`) copy its ~15MB of runtime assets into `frontend/public/vad/` (gitignored, regenerated on every dev/build run — not tied to `npm install`, since the Docker build's `npm ci` layer runs before the rest of the source, including this script, is even copied into the image). Known gap: this currently fails under `npm run dev` specifically — Vite 5's dev-server import-analysis 500s on onnxruntime-web's dynamically-imported `.mjs` WASM glue (a dev-only Vite/onnxruntime-web interaction, unresolved so far). The production build (`npm run build`, served by the backend) is unaffected — use that path when testing VAD/turn-taking changes.
- Local backend: `uvicorn backend.app:app --reload`
- Docker: `docker compose up --build` (builds the frontend too, via a multi-stage Dockerfile; serves on `http://localhost:8391` — a deliberately non-standard host port, mapped to the container's 8000, set in `compose.yaml`). Add `--watch` to pick up code changes automatically (`develop.watch` in `compose.yaml`): backend edits are synced into the running container and the app restarted, without a full rebuild; frontend edits and `requirements.txt` changes trigger a rebuild instead.
- Copy `.env.example` to `.env` and fill in real values before running — `.env` is gitignored and read via `env_file` in the compose file, and by Vite (`envDir` at the repo root) for the `VITE_OIDC_*` build vars.
- Keycloak (ADR 0009): `docker compose up` starts a local Keycloak on `http://localhost:18081` and imports `keycloak/direkt-realm.json` (client `calltrainer-frontend`, dev users `alice`/`bob`/`carol`, password = username). Edit the JSON → wipe the volume to re-import: `docker compose down -v` (or `docker volume rm direkt-calltrainer-keycloak-data`). `KC_HOSTNAME` pins the token issuer to `localhost:18081`; the app container reaches the realm's keys over the compose network via `OIDC_JWKS_URL` (`backend/auth.py`). Keycloak admin console: `admin`/`admin`. For a host-only `uvicorn` run, point `OIDC_ISSUER` at the same URL and drop `OIDC_JWKS_URL` (the host can reach `localhost:18081` directly).
- There is no LLM mock any more — `scripts/mock_llm_server.py` was removed in commit 113394f and never replaced, so anything touching STT/LLM/TTS needs a reachable `DIREKT_URL`. To exercise the wrap-up generator without one, stub `backend.clients.llm.complete`.
- Checking the pipeline backends: `python scripts/check_backends.py` fires one minimal real request at each configured STT/LLM/TTS backend and logs OK/FAIL per step (exit 0 only if all pass); it respects the `DEBUG` toggle (forces the TTS check onto the DiReKT fallback instead of KugelAudio). The app runs the same check (`backend/clients/health.py:check_backends`) at startup from the `lifespan` handler — a dead model is logged as `Startup check: <STEP> FAILED` but does not stop the app from booting.
- Feedback worker: `docker compose up` now also starts `redis` and a `worker` service running `python -m backend.worker`. The worker shares the app's image and database but no request cycle; if it is down, calls still work and wrap-ups simply queue. RQ forks per job, so the worker only runs on Linux — use the container, not a host process, on Windows.
- Database: the app migrates to head and seeds the reference tables itself at startup (`backend/db/provision.py`, called from the `lifespan` handler), so `docker compose up` needs no manual step — a provisioning failure is logged as `Database provisioning failed` and does not stop the app, but every Session then fails to persist and silently loses its Feedback. To do it by hand against a host-side database, `docker compose up -d db` then `python scripts/seed_reference_data.py`, which is a thin CLI over the same `provision()`. Both read `DATABASE_URL` from `.env` and call `load_dotenv()` themselves; `backend/db/session.py` does not — it reads `DATABASE_URL` lazily, on the first call to `session_scope()`/`get_engine()`, so importing it never requires an environment. The `DATABASE_URL` in `.env` points at `localhost` for these host-side calls; the app container gets its own URL pointing at the `db` host, set in `compose.yaml`.
- Schema changes: edit `backend/db/models.py`, then `alembic revision --autogenerate -m "..."`. **Always read the generated migration before applying it** — autogenerate adds `NOT NULL` columns without backfilling, which fails on non-empty tables, and it leaves unique constraints unnamed, which makes `downgrade()` unrunnable. The ER diagram is regenerated automatically on every docs build (see below); `python scripts/generate_erd.py` refreshes `docs/er_modell.png`/`.svg` on demand and needs the Graphviz `dot` binary (`brew install graphviz`).
- Docs site (arc42 + ADRs): `mkdocs serve` (serves on `http://localhost:8000`; the app is on `8391` now, so no clash). `mkdocs build` writes static output to `site/` (gitignored).

- Tests: `pip install -r requirements.txt` then `pytest` (config in `pytest.ini`, suite in `tests/`). Feature-traceable backend tests — every file cites the `F-xx`/`R-xx`/ADR it proves; see `tests/README.md` for the traceability matrix. No network, DB, credentials or browser needed: the STT/LLM/TTS pipeline backends are faked in `tests/conftest.py` and the REST layer runs over an in-process ASGI transport. `tests/test_documented_gaps.py` deliberately asserts the *current* MVP state (no UI language switch, no cross-session history endpoints) so a test there starts failing when that gap closes. Frontend has no JS test runner configured.
