# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Calltrainer is an AI-powered phone conversation trainer that provides real-time analysis and behavioral feedback during simulated calls (from README.md).

## Current State

FastAPI backend (`backend/app.py`) serves the API and, once built, the React + TypeScript frontend (`frontend/`, built with Vite; the backend serves `frontend/dist`). The SPA has a router (`react-router-dom`, paths in `frontend/src/routes.ts`): `/` is the training flow, `/profil` the account screen, `/trainings/:sessionId` one past training, and `/impressum`, `/datenschutz`, `/barrierefreiheit` the legal pages the footer links (`components/legal/`, shared frame in `LegalPage.tsx`). Imprint and accessibility statement are the EFRE DiReKT project's own texts, adopted unchanged apart from one scope sentence; the privacy statement is adapted to what this application actually processes and **still carries a visible draft banner plus two marked gaps** (KugelAudio's seat and DPA, the server's location) that need filling in and DPO review before it is published. `/hinweise` carries the AI disclaimer (you are talking to a machine, it invents things, the wrap-up is not an assessment, do not say other people's data aloud). The privacy statement names the real processors: Hetzner Gunzenhausen as hoster and KugelAudio UG Hannover for the speech output, both under Art. 28 agreements, with KugelAudio's own sub-processors in Germany and Finland. **ADR 0020 says the deployment is a university server; it is actually Hetzner** — the ADR carries a status update saying so. DPO review of the privacy statement is still outstanding. The profile screen carries the history (F-48): `useSessionHistory` reads `GET /api/sessions` one page at a time and appends on demand (de-duplicating by id, because offset pagination shifts rows when a Session is written mid-browse), `SessionHistory` renders one row per training, and a row links to `PastSessionView`. Only the **four** newest rows are shown; the rest are behind one "Ältere Trainings anzeigen (n)" toggle, and the pagination button appears only while that is open (a collapsed list must not offer to fetch rows it is not showing). Every row carries its own delete control — a bin button *beside* the link, never inside it (a `<button>` nested in an `<a>` is invalid and would navigate as well), which opens an inline confirmation under that row and, on success, drops the row locally via `useSessionHistory`'s `removeSession` rather than refetching, because re-requesting the same offsets after a row disappeared would skip one. That screen reads the Session **once** (`useStoredSession`) and never polls — the polling in `useSessionFeedback` is right only for a call that just ended, where a wrap-up genuinely is on its way (ADR 0019); on a days-old Session it spent a minute claiming one was being created and then called it a failure. `FeedbackView` is therefore split into the polling wrapper (unchanged for the live flow), a presentational `FeedbackReport`, and a `MetricSection` — a stored Session with no wrap-up still shows its Kennzahlen and Transcript, because those are in the database regardless. Note that a missing wrap-up is **not** missing for want of audio: the generator works from the Transcript and the stored Measurements (ADR 0049), so the ~13 Sessions currently stuck on `queued`/`failed` could still be generated later. Because those paths exist only in the browser, `app.py`'s `SinglePageApp` falls back to `index.html` for unknown paths — but never under `/api`, `/ws` or `/health`, and never for a path that looks like a file, so an unknown endpoint stays a 404 instead of answering a script tag with HTML (`tests/test_spa_routing.py`). Keycloak always redirects back to the origin, so returning to the requested page is the app's job: `onSigninCallback` in `main.tsx` strips the `?code=&state=` and stores the path, and `<ReturnToRequestedPage>` navigates *through the router* — `history.replaceState` fires no event a router would hear, which is the trap here. The header's brand link and account chip are suppressed during the mic check and the call (`navigationLocked`): leaving the page tears down the WebSocket, and an abandoned Session is never persisted (ADR 0034). The profile screen is read-only by construction — identity lives in Keycloak and there is no local User table (ADR 0031), so it renders ID-token claims via `useAccount` and says so; it carries the F-49 privacy notice, the consent and retention switches, **the Fokusziele section (F-61, below)**, the data overview, and a deletion section that names the three real paths (one training from its row in the history or from its own page, all of them by withdrawing consent, the whole DiReKT account by mail). **Fokusziele (F-61, ADR 0074)**: a User picks **at most five** training focuses from a shipped catalogue of 15 in 4 groups — asked once at first start (`FocusDialog`, and **Ohne Fokus fortfahren** is a full answer), changed afterwards in the profile (`FocusSettings`); both render the same `FocusGoalPicker`. Three tables: `focus_goal` is a reference table seeded from `seed_data.py`'s `FOCUS_GOALS` (German display text lives in the row, like a Scenario's title; retired rows are deactivated, never deleted), `focus_selection` records *that* a subject answered — its own row, because "picked nothing" and "was never asked" must be distinguishable or the dialog re-opens forever — and `focus_selection_goal` holds the picks. `backend/focus.py` is the single place all three are read and written, always scoped to the caller's `sub`; `MAX_GOALS = 5` is enforced there (a sixth goal is a **400**, never a silent truncation) and travels to the client in every `/api/focus` payload, so the picker disables the sixth checkbox using the backend's own number (ADR 0063's pattern). `GET /api/focus` serves catalogue *and* selection in one response — the dialog needs both and two requests would render half a state; `PUT /api/focus` replaces the whole set (hence PUT, unlike `/api/consent`, which appends). Every goal carries `evidence` (`measured` / `mixed` / `interpretive`), which records how far it is derivable today and **stays internal** — not on the wire, not on a card: the aim is that every goal becomes measurable, and asking the User to weigh that up while picking would push an implementation detail into their choice. The obligation it stands for moves to whatever eventually *reports* on a focus, which may only claim what is actually behind the goal (ADR 0004/0051). A focus is a **setting, not training data** — no consent guard (declining consent must not also cost you the setting) and `deletion.py` deliberately never touches it, which a test pins. `FocusProvider` nests inside `ConsentProvider` in `main.tsx` so the two first-run questions come in order, legal one first, and neither blocks on a *failed* load. **Nothing reads a selection yet**: the wrap-up prompt, the setup screen and the (unbuilt) dashboard all ignore it, and no catalogue text claims otherwise — that hookup is the next step and inherits the constraint that it may only say what a goal's `evidence` allows. `/health` is liveness only (touches nothing, so a brief database outage cannot look like a dead process) and `/health/ready` is readiness (checks the database) — the compose healthcheck asks the latter, because an instance that cannot reach Postgres can only answer 503. `/api/personas` and `/api/scenarios` (their own routers, `backend/api/personas.py` / `scenarios.py`) list the Persona/Scenario options shown before a Session starts — any Persona can run any Scenario, no compatibility to filter by. **Both read from the `persona`/`scenario` tables, not from Python lists** (ADR 0041), and serve only rows with `active` set: `backend/personas.py` and `backend/scenarios.py` hold the value types only — their hardcoded lists are gone; the seed content lives in `backend/db/seed_data.py`, and `backend/library.py` is the single place the tables are read, written and mapped onto those types. Rows dropped from the seed are deactivated rather than deleted — `session` references them by foreign key, so a past Session has to stay readable. **Users author their own Scenarios** (ADR 0024 → ADR 0058), but **not Personas** — a Persona is a curated character with a fixed voice, so `/api/personas` stays read-only. Authoring (ADR 0058): each row carries `created_by` (Keycloak `sub`, NULL for a built-in), `visibility` (CHECK-enforced) and an unguessable `extern_id` (ADR 0050) — which is what the client sends in `session.start`, never the `key` slug (nullable now). `POST/PATCH/DELETE /api/scenarios` and `GET /api/scenarios/{id}` are owner-scoped by the verified `sub`; a 404 and a 403 are the same answer. `POST /api/scenarios/document` (F-58, `backend/documents.py`, `pypdf`) extracts the text from an uploaded **text-layer** PDF (no OCR) and has the LLM (`llm.complete`) condense it into a short German fact list for the editor's Fakten field — stateless, the file is never stored; `summarised: false` in the response means the LLM was down and the raw truncated text came back instead. Deliberate simplification over ADR 0005/0024's "uploads route through the Data Platform". The **second** way an authored Scenario comes about is the *Folgeszenario* (F-60, ADR 0069, `backend/followups.py`), and **nobody asks for it**: every finished Session whose wrap-up names `improvement` points gets exactly one, written by the LLM in the Feedback worker right after `generator.py` stores the wrap-up and closes the job, and stored through `library.create_scenario` like anything hand-authored — `created_by` = the Session's `subject_id`, `visibility` = `private`, `tenant_id` NULL (the worker has no `tenant` claim; sharing stamps the row later). No points, an unreachable model or a reply that yields no usable draft means no follow-up, silently — the wrap-up is what the User is waiting for. Provenance is the new `scenario.derived_from_session_id` (nullable FK, indexed, **UNIQUE** so `scripts/requeue_feedback.py` cannot produce a second), and the card carries `follow_up: boolean` beside `origin: "own"`, the pattern `shared` uses. A follow-up leaves the library when its Session goes — one training deleted, consent withdrawn, or the six-month sweep — as `active = False`, never a row delete, because a later Session may have been played on it and `session.scenario_id` is NOT NULL (ADR 0026). `backend/deletion.py::retire_follow_ups` is the one place that decides that; the FK's `ON DELETE SET NULL` clears the provenance beside it. No consent guard is needed anywhere in this path: no consent → no stored Session → no Feedback → no follow-up. What the prompt is *not* given is deliberate: not the measured statistics (a Scenario correcting a figure needs the target range ADR 0051 declined to invent) and not the played Scenario's four prompt fields (ADR 0043 withholds a built-in's case from the client; a readable draft must not be the way around that) — only its card, `title` + `short_description`, which fixes the subject area. The prompt keeps the exercise's purpose out of those four fields, since they become the simulated caller's briefing and a caller who knows what is being trained gives the answer away; the card may say it, and the card never reaches the prompt. Apart from the badge, a follow-up is an authored Scenario like any other: editable, shareable, playable against any Persona. Prompt safety (ADR 0059): authored text is sanitised at the write boundary (`backend/authored_text.py`) — `[CALL_END]`/bracket-token/fence-run stripping — and an authored Scenario adds one prompt line (`AUTHORED_SCENARIO_NOTE`) framing its text as information, not instructions. Company sharing (ADR 0060): `tenant_id` (the author's company, resolved per request in `backend/tenants.py` from a `tenant` claim — a Keycloak user attribute an admin sets at account creation, put in the token by the `calltrainer tenant` protocol mapper; no claim, or an unknown value, means the seeded `default` tenant), `visibility` widened to `private | tenant | public` with a second CHECK tying `tenant` to a non-NULL `tenant_id`. `backend/library.py` scopes every Scenario read to the caller's `sub` + `tenant_id`; the client never supplies either. Sharing is one `PUT /api/scenarios/{id}/visibility` toggle (`private` ↔ `tenant`; `public` needs review, not built). `GET /api/tenant` returns the caller's resolved company name (or `null` for `default`) so the setup screen can show the five scenario filters — **Alle / Standard / Individuell / Folgeszenario / `<Unternehmensname>`**, where "Individuell" means hand-authored — and badge company scenarios with the real name. Those origin chips are **level 1** of a two-row filter (ADR 0072), rendered by `frontend/src/components/FilterSlider.tsx`; **Folgeszenario** is the fifth option, and it is `origin: "own"` on the wire with `follow_up` set rather than an `origin` of its own. `GET /api/scenarios` orders by that same level-1 grouping, then by `created_at` (`library.list_scenarios` sorts, `api/scenarios.py` groups on top of it with a stable sort). **Level 2** is the thematic **category slider**: four values refining F-03's three call contexts, `operations` / `requirements` / `pricing` / `closing`, labelled Betrieb & Störung / Beratung & Anforderung / Preis & Kondition / Abschluss & Einwand (F-03's offer-and-pricing context is split, because talking a rate down and getting to a signature are different exercises; the seed lands 6/5/3/3). Both rows are the same component, so they cannot differ in size; each option shows how many Scenarios it would yield under the *other* row's selection, and both are `radiogroup`s with a sliding thumb rather than an `<input type="range">`, because the options are nominal. `scenario.category` is a CHECK-enforced closed vocabulary (`SCENARIO_CATEGORIES` in `models.py`, and the API's request pattern is derived from that same tuple), nullable, display-and-filter only — the prompt never reads it, exactly as it never read the free-text `scenario_type` column it replaces; what changed is that this one has a vocabulary and a consumer. The seeded library holds 17 Scenarios: the original five plus the scenario catalogue's S-01–S-05 and S-07–S-13. S-06 (needs the cross-Session memory of F-23, not built) and S-14 (not a Scenario — since ADR 0043 the language belongs to the Persona) are deliberately not seeded. The scenario card also carries `shared` (shared with the company): the author's *own* shared Scenario stays `origin: "own"` (still editable) but `shared: true`, so the `<company>` filter includes it and its badge reads "Individuell · geteilt" (the badge/filter is labelled "Individuell" in the UI; the `origin` wire value is `own`). The `persona` table carries the same columns for schema symmetry but nothing writes them. Pilot tenants (`solox`, `appollo`, `default`) are seeded; Keycloak Organizations (ADR 0060 phase 2) is an optional richer source for the same `tenant` claim, not a prerequisite. Auth is Keycloak/OIDC (ADR 0009, now built): the SPA logs in with PKCE against the `direkt` realm (`calltrainer-frontend` client) — `frontend/src/AuthGate.tsx` blocks the app until authenticated, `AppHeader` shows an account chip linking to `/profil`, where the "Abmelden" button (`signoutRedirect`) now lives. `backend/auth.py` verifies the bearer JWT (`OIDC_ISSUER`, audience `calltrainer`) on `/api/personas`, `/api/scenarios`, `/api/tenant`, `/api/sessions`, `/api/consent`, `/api/focus`, `/api/me/*` and the `/ws/session` handshake — the WebSocket carries the token in its `session.start` message since a browser can't set a header on it. `/health`, `/health/ready` and the static frontend stay open. No role checks. `docker compose up` brings its own Keycloak on `:18081` (`keycloak/direkt-realm.json`, dev users alice/bob/carol). There is no Language selection: each Persona has exactly one fixed Language/voice (stored on the `persona` row — `language_code`, `tts_voice`, `kugelaudio_voice_id`), and German and English are both supported, per Persona — the language picks a `LanguagePack` (`backend/session/language_packs.py`) carrying the closing-intent patterns, the opening examples and the fallback closing line, so a further language means a pack plus a Persona naming it, never a global setting. The live Session itself runs over a per-Session WebSocket at `/ws/session` (`backend/api/session_ws.py`): the client streams one full Turn of recorded audio at a time (browser-side voice-activity detection ends each Turn automatically, no manual button) and the user can talk over the persona to cut a reply short (barge-in, ADR 0035 — the client silences everything streamed ahead at a master gain, the history keeps only the heard words plus a cut-off dash, the transcript line gets `... [unterbrochen]`, the cut-off sentence is filtered out of the next reply in every form — restarted from the top (`repetition.resumes`, first 3–5 words), continued mid-sentence (lower-case first chunk), or verbatim — with one `RESUME_NUDGE` re-ask if the reply was nothing else (`_ReplyFilters`, `_note_suppressed`; the heard-text math lives in `backend/session/heard.py`), and the *next* Turn carries `INTERRUPTED_NUDGE` — spliced in *before* the user's message and quoting nothing, because the 4B model continues from whatever sits last in its context — so the model answers the user instead of finishing its cut-off sentence or re-introducing itself; a reply that opens by reading the user's line back is cut to the answer before synthesis (`repetition.strip_echoed_prefix`, ≥3 words in order); the per-Turn nudges all live in `backend/session/nudges.py`, the system-prompt builders in `backend/session/prompting.py` — `orchestrator.py` sits under a 1000-line pylint ceiling, which is why both moved out; a reply that *opens* with a sentence the persona already said is regenerated once before synthesis (`REPEAT_OPENING_NUDGE`), the sibling of the re-greeting guard, so a loop costs a retry rather than the loop guard's goodbye; sentences the persona already said verbatim are dropped from a chunk before synthesis (`repetition.drop_said_sentences`), on guarded attempts only; an *unprompted* `[CALL_END]` on a reply whose last sentence still presses or asks is vetoed (`still_pressing_re` per language pack, farewell wins — ADR 0037), and the chunk is cut *at* the marker so nothing after it is spoken; `orchestrator.ended` is set the moment a reply ends the call and `session_ws` ends the Session on a barge-in over that goodbye instead of reviving it). **What the model reads is not the history (ADR 0071):** `_messages_for_turn` sends the system prompt, a system message with *the caller's notes* (one background `llm.complete` per completed exchange, `prompting.build_state_prompt`, refreshed again when a barge-in trims the reply; a failure keeps the stale notes) and only the last `HISTORY_WINDOW` (6) messages verbatim — `_messages` stays the full record for the guards, the trims and the Transcript, and `orchestrator.close()` cancels a refresh in flight. The system prompt itself is short and sectioned (same ADR; the ~30 assertions in `tests/test_system_prompt.py` pin what it must still say). A Whisper phantom transcript ("*Titelm*", "Vielen Dank." — `stt_phantom_re` per language pack plus a language-independent annotation pattern) is no Turn: no reply, no history entry, back to listening; the server runs each Turn through STT → streamed dialogue generation → chunked TTS (`backend/session/orchestrator.py`, `backend/clients/`), and streams synthesized audio back chunk-by-chunk so playback can start before the full reply is done generating (ADR 0033, which supersedes the earlier non-streaming pipeline; ADR 0044 refines the TTS leg — each chunk is forwarded to the client sub-chunk by sub-chunk as KugelAudio's `stream_async` produces it, not buffered. **Never leave a `stream_async` short of its `final` frame on the pooled socket:** its frames carry no request id, so the next request reads the previous one's audio — a persistent one-chunk offset. `synthesize_stream` drops and re-warms the pooled connection on any unfinished exit, and `_speak` `aclose()`s an abandoned stream immediately; ADR 0044's amendment has the story). STT and LLM call the same OpenAI-compatible DiReKT model gateway, configured via a single `.env` base URL/key pair (`DIREKT_URL`, `DIREKT_API_KEY`) plus one model name per step (`STT_MODEL`, `LLM_MODEL`) — neither has a fallback. TTS defaults to KugelAudio (a separate SDK, not an HTTP endpoint on the DiReKT gateway; `KUGELAUDIO_API_KEY`/`KUGELAUDIO_MODEL`), falling back to the DiReKT TTS model (`TTS_MODEL`) if KugelAudio fails, or always if `DEBUG=True` is set (`backend/clients/config.py`). No text is shown during the live call, only a state animation (listening/thinking/speaking) — the full Transcript is sent once, at the end, and shown as a post-call summary. Persistence lives in `backend/db/`: `models.py` holds the SQLAlchemy schema, `base.py` the declarative base carrying the constraint naming convention, `session.py` the `session_scope()` context manager used for all database access (it assembles the connection URL from the `POSTGRES_*` settings, lazily), `migrations/` the Alembic revisions, and `provision.py` the migrate-and-seed step the app runs at startup. Postgres runs as the `db` service in `compose.yaml` (ADR 0010). The backend test suite lives in `tests/` (pytest, feature-traceable — see the Tests section under Build / Run); the frontend has a narrow Vitest suite covering only the live-call audio path (`frontend/src/**/*.test.ts`, see Build / Run). `docs/arc42.md` is filled in.

**Table and column names, and the wire, are English throughout (ADR 0026, ADR 0057, extended to the Scenario library / authoring surface by ADR 0061).** The schema says `turn.speaker` in `('user','persona')` and `feedback_point.kind` in `('strength','improvement')`; the JSON the frontend reads uses the same keys and the same values, exactly as `frontend/src/protocol.ts` declares. `backend/api/sessions.py` passes the ORM's own values straight through — there is no translation boundary any more on that surface. The Scenario library / authoring wire (`backend/api/scenarios.py` ↔ `frontend/src/scenarioLibrary.ts`) matches the schema too since ADR 0061: `visibility` (`private`/`tenant`), `origin` (`builtin`/`own`/`tenant`), `shared`, `short_description`/`description`/`case_facts`/`call_goal`/`success_condition`, `pages`/`summarised`, `category` (ADR 0064), `follow_up`/`derived_from_session_id` (ADR 0069), and the routes `PUT …/visibility`, `POST /api/scenarios/document`, `GET /api/tenant`, `GET /api/scenarios/field-limits` (ADR 0063: the editor's per-field `maxLength` comes from `backend/authored_text.py` `FIELD_LIMITS`, not a bundled copy) — the card field `name` (the `title` column) is the one non-1:1 mapping, in `ScenarioInput.to_library()`. German remains only in genuinely user-facing content (Persona/Scenario text, metric display *names*, editor field labels, the wrap-up prompt's own written language) and in the documentation. Every constraint and index name comes from the naming convention on `Base.metadata` (ADR 0053), every foreign-key column is indexed (ADR 0052), and ownership edges carry `ON DELETE CASCADE` with `passive_deletes=True` on the ORM side, so deleting a Session removes its subtree by raw SQL as well as through the ORM, while reference tables deliberately do not cascade. Vocabularies (`session.status`, `turn.speaker`, `feedback_point.kind`, `analysis_job.kind`/`status`) are enforced by CHECK constraints rather than Postgres ENUMs. `session.extern_id` is the unguessable UUID the client sees (ADR 0050); the primary key stays internal. The migrations and the ER diagram in `docs/datenmodell.md` are generated from `models.py`, not edited by hand; the schema's rationale is in ADRs 0025 through 0032, 0050, 0052 and 0053.

Post-call analysis lives in `backend/feedback/` and produces **one set of statistics per Session, never per Turn** (ADR 0051): F-53's Kennzahlen — Redeanteil, Fragen, Sprechtempo, Wortanzahl, Reaktionszeit, Sprechpausen — plus F-37's loudness curve, F-35's Sprachmelodie. That one is **four factors, not one figure** (`backend/feedback/intonation.py`): Umfang (5th to 95th percentile in **semitones**, not Hertz, so the same expressive range reads the same for a low and a high voice), Bewegung (semitones per second, which is what separates a wide-but-drifting contour from a lively one; computed **per utterance and pooled**, never across the flat call contour, because the last frame of one utterance and the first of the next are neighbours in that array and a Persona turn apart in the call, and on a **30 ms median-smoothed** contour, since 2% frame-to-frame tracker noise inflated the raw figure by a third while smoothing costs the real movement 5%), Satzenden (falling/rising/level per utterance, read by least-squares slope over the last 400 ms of *voiced* frames) and Verlauf (first vs last third of speaking time). The endings carry an interpretation because a slope has a natural zero and needs no population norm. The **Umfang carries a five-step reading** — stark monoton / monoton / ausgewogen / lebendig / überzeichnet, boundaries at 4/7/12/18 semitones (`intonation.liveliness`, `liveliness_steps`) — which is the second deliberate exception to ADR 0004/0051 beside the traffic light below: asked for explicitly, presented as an *Einschätzung* with its whole scale visible and the current step marked, and kept off the dashboard. The boundaries are the F0 standard deviations usually reported for speech (≈1 st monotone, 2–3 conversational, ≥4 animated) converted to a 5–95 span (≈3.3 SD); that conversion is the entire derivation. Deliberately **no colour** on those five steps, unlike the traffic light: the scale is uncomfortable at both ends, so there is no direction for a colour to point in. The step is **not stored** with the Measurement — `api/sessions.py::_served_detail` derives it from the stored figure on every read, so a recalibration reaches trainings whose audio is long gone (ADR 0048) instead of leaving them labelled by a scale that no longer exists; Bewegung stays a figure with no adjective, because nothing published anchors a boundary for it. A step needs `MIN_VOICED_MS_FOR_READING` (10 s) of **voiced** speech under it — the figure is reported from 0.2 s upwards, but five steps read off two seconds of humming would be a verdict on nothing, so below the floor the block says how little was spoken instead. Two defects found by audit and fixed: the pitch was analysed on the loudness curve's **100 ms grid**, which aliases intonation (a 16-semitone contour read as 14.2 at 3 Hz and 4.8 at 8 Hz) — it is now Praat's 10 ms, thinned to 100 ms only for the stored curve; and a single fixed floor/ceiling admitted octave errors (a 116 Hz voice produced a 483 Hz frame) — now a **two-pass measurement**, the second pass windowed on the first pass's own quartiles (De Looze & Hirst). **The whole reading sits in the wrap-up itself** (`IntonationSection.tsx`, rendered by `MetricSection` under the Kennzahlen grid on both the post-call screen and a stored training): figure, scale, contour, the four factors, the note. It is the one Kennzahl with a block instead of a tile, because what it measures is a shape and a tile can only carry a number; the Kennzahl's own page still exists for a deep link and shows the same block. `PitchContour.tsx` draws the contour the way phonetics does: semitones relative to the speaker's median, the speaker's own 5-95 band behind it (from `band_low_st`/`band_high_st`, **measured at both ends** — a voice does not reach as far down as up, and the old ±range/2 drew the band on that assumption), one hue, and 6% headroom so an extreme does not sit on the frame. Its horizontal axis is **the user's speaking time, not call time** — the curve holds the user's frames only, so no stretch of it stands for the Persona talking; where one of the user's utterances ends and the next begins there is a light-grey **dashed vertical line** instead of a gap, numbered while the numbers still fit (`intonation.utterance_breaks` → `detail.turn_breaks`, indices into the thinned curve, deduplicated per window). Unvoiced frames are **bridged rather than left as holes** — the earlier hole-per-consonant version broke the line into confetti — but the bridges are dotted and faint and never cross a seam, so the drawing stays continuous without claiming a measurement where there was none (which is the commonest way an F0 plot lies). Two things about resolution, both found by rendering real measurements rather than by reading the code: the curve is stored at **50 ms** (`PITCH_INTERVAL_MS`), not at the loudness curve's 100 ms, because ten samples a second alias a syllable rate of four to five and turn the drawing into a sawtooth; and the component **condenses to one point per unit of plot width** by column median, because two minutes of speaking time is 2400 points across 676 units and the line otherwise grows hair that is rendering noise. `intonation.effective_step_ms` is what the stored `curve_step_ms` and the seam indices are in — thinning works in whole 10 ms frames, so a request for 25 ms yields 20 ms, and the axis was briefly labelling a 19 second contour as 24 seconds. Those last are classified, not just counted (`backend/feedback/interruptions.py`, pure functions over a `Segment` timeline, so they can be recomputed for stored Sessions — the timeline is persisted even though the audio is not): a user start inside a Persona window is a **backchannel** (short and cost the Persona nothing), **terminal** (inside `TERMINAL_WINDOW_MS` = 200, Stivers et al. 2009's turn-taking gap), **hard** (deep, and the reply was actually trimmed) or **soft** (deep but nothing was lost). First rule wins, and the order is the point: counting a backchannel would punish good listening. Two facts about this architecture shape it — a Persona's end is *modelled from dispatched audio* and is **not** shortened by a barge-in, so "did the Persona yield" cannot be read off the timeline and `turn.interrupted` (a real column since migration `e7b3d9c1a542`, not the display marker) is the discriminator; and short backchannels never reach the server at all, since ADR 0036 put a 500 ms VAD floor in the browser. `interruptions` is the hard count, and the drill-down on its tile shows each one as transcript: the Persona's cut-off line, a visible break where the user came in, and **what the Persona had been about to say**, struck through. That last part exists because `turn.unheard_text` (migration `a91c5f70d8e3`) now keeps what had been synthesized but not yet played — deliberately *beside* the transcript and out of the model's history, since ADR 0035 keeps both to the heard words exactly; it is NULL for calls recorded before that, and the block says so. Backchannels are reported beside the count and never against it (they cannot buy an interruption off, which would invent a trade), and the call length and Persona-turn count travel as context. The metric stays a **count**: a rate per Persona turn was built alongside it and dropped again, because at the length these calls actually run (6 to 9 Persona turns) a single interruption already gave 0.11 to 0.17, so every call with one landed on the top step and green was unreachable except at zero — the denominator was saying more than the call was. `persona_turns` travels in the detail as context instead. Each hard interruption also writes a **`Finding`** row, which gives that table its first writer and reader: a Finding is an event that occurred at a moment, not a value judged against a threshold, which is what keeps it inside ADR 0051. `scripts/backfill_interruptions.py` computes all of it for Sessions stored earlier. **The traffic light on `interruptions` (`GREEN_MAX_COUNT` = 0, `YELLOW_MAX_COUNT` = 2) is a trial and contradicts ADR 0004/0051/0065** — it was asked for explicitly, the ADRs were deliberately left unchanged for now, and it is confined to one chip on the single-call view (never the dashboard, whose no-judgement rule ADR 0065 states outright). The light colours **the figure only**, never the whole tile (that would shout an orientation two invented numbers cannot support, and drown out the eight neighbouring Kennzahlen that judge nothing); the step is written out underneath, and the three-step scale it comes from sits on the Kennzahl's own page (`metric_scales` on the detail route, built from the constants so a recalibration reaches the legend too). `metric_scales` is one shape for both readings — `{step, label, range, light}`, `light` null where the scale has no direction — and the German wording travels with it, so the labels live beside the thresholds they describe rather than in a second table in the frontend. Clicking such a tile opens **its own route**, `/trainings/:sessionId/kennzahl/:metricKey` (`SessionMetricView.tsx`), not an in-place panel: the excerpts run several lines each and a reader should be able to link to them and use Back. Easy to remove: the `TrafficLight` class, its two constants, the `metric-light` branch and one CSS block. Filler words were investigated and **deliberately not built**: across the stored transcripts not one "äh"/"ähm" survives, because Whisper normalises them away, so the metric would measure the recogniser's cleanup and report near zero for everyone. `acoustics.py` is the only module that imports `parselmouth`; it measures one Turn's audio inline in the live path (on a worker thread *alongside* the STT round trip, so it costs no latency) and returns raw, concatenable facts (ADR 0047/0048): duration, phonation, pauses, and two curves on one shared 100 ms grid — loudness and, since F-35 was built, pitch. Adding a paraverbal metric is that pattern: a curve on `TurnAcoustics` (no defaults on that dataclass, so every construction has to be revisited), `Turn`/`Conversation` concatenate it, a deriver plus a `MetricDef` in `metrics.py` seeds it automatically. **The audio is never stored (ADR 0048), so a new measurement cannot be backfilled over past trainings** — it starts on the day it ships. `tests/test_acoustics.py` is the one place real Praat runs, against synthetic tones with known answers. `metrics.py` owns the metric inventory, which `provision.py` also seeds, so the two cannot drift — adding a metric is one `MetricDef`. Its metric *keys* are English (`talk_share`, `pace`, `loudness`, …); only their display `name` (e.g. "Redeanteil") stays German, because that is what the UI shows. **No metric carries a target range**: none is validated for this population, and an invented threshold is a score in disguise (ADR 0004/0051), so nothing writes `Finding` rows and the wrap-up prompt forbids judging a figure against a norm. **Nothing in the Feedback is measured against the Persona** either — it is a synthesized voice, so comparing the user to it would report a TTS setting as if it described the user (ADR 0051). `session/models.py` owns the Turn timeline: a Turn is one exchange in memory, but `utterances()` flattens it to one row per speaker for storage, which is what gives every line its own offset and makes the Gesprächsprotokoll timestamped; `conversation()` folds the call for `metrics`. Each speaker's speaking window is tracked separately so the gateway's latency is charged to neither: Reaktionszeit runs from when the Persona stopped speaking, and the Session clock starts at the client's `session.activate`, not at connect. **Storage requires consent (ADR 0066).** `backend/consent.py` is the single place that answers whether a subject's Sessions may be written; `api/session_ws.py::_record` asks it immediately before persisting — at write time, not at the handshake, so a withdrawal *during* a call still takes effect — and it **fails closed**, unlike every other database call in the app, because the alternative is storing data on a guess. The `consent` table is append-only (grant → withdraw → grant is three rows, newest wins) and versioned: bump `CURRENT_VERSION` when the notice changes and every earlier decision goes stale and is asked again. Declining leaves the trainer fully usable — the call runs and the transcript is shown, only storage, wrap-up and history are absent — which is what makes the consent freely given rather than coerced; `SetupView` says so *before* the call. Withdrawing deletes: `backend/deletion.py` removes the subject's Sessions in the same transaction as the decision, leaning on ADR 0026/0052's cascades. **Sessions expire after six months (ADR 0067).** `backend/retention.py` holds the period (`RETENTION`, pinned by a test) and the sweep; `retention_preference` carries a row only for subjects who switched it off, so the *absence* of a row is the default and the period applies to everyone who never touched it. `app.py`'s `_retention_loop` runs the sweep at startup and daily after, driven from Postgres rather than from a scheduled Redis job that would not survive a restart; `scripts/apply_retention.py [--apply]` is the manual path. Switching the sweep back on deletes nothing on the spot, so the control stays a statement about the future rather than a delete button in disguise. The consent log is **not** swept and **not** deleted by any deletion path (ADR 0068): it holds decisions, not their subject matter, and it is the only evidence that the storage which did happen was permitted. Say "your trainings are deleted", not "all your data". Alongside it: `GET /api/me/data` (counts and period — the *extent* of what is held), `GET /api/me/export` (every row the subject owns, nested JSON, served as a download so a page of transcripts is not left in a tab) and `DELETE /api/sessions/{extern_id}` for one training, which 404s for an id that is absent *or* not the caller's, exactly as the read route does. **Spoken content no longer goes into the log by default**: `clients/stt.py` logs the transcript's *length* (which still catches an empty transcript or Whisper's near-silence hallucination) and the text itself only under `LOG_TRANSCRIPTS`, off unless set and announced with a boot warning while on — that log is outside every deletion path, so it is a default and not a guarantee. Backups are not reached because **there are none** — no backup service in `compose.yaml`, no `pg_dump` in the repository, Postgres on a Docker volume. Whoever introduces backups has to add a retention policy to ADR 0066 in the same change, or a deletion that is complete today quietly stops being so. `persistence.py` writes it all in one transaction after the call has ended, never during it (ADR 0034) — a Session the client abandoned mid-call is deliberately not persisted, and a database failure is logged but never fatal, since the Transcript is already in memory and gets sent either way. `generator.py` produces the wrap-up in the RQ worker (ADR 0049), and `GET /api/sessions/{extern_id}` (ADR 0050, behind the same bearer token as the rest of `/api`, and only for the caller's own Sessions: the route compares `session.subject_id` with the token's `sub`, and someone else's `extern_id` answers 404 exactly like an unknown one, because a 403 would confirm the id exists — ADR 0031/0050) serves it to the post-call screen, which polls (`useSessionFeedback`, `FeedbackView`). That wrap-up carries **four** fields, not three: alongside the summary and the two point lists, F-42's `phase_language` paragraph says whether the register moved with the phase of the call (warm → sachlich → warm across Opening, Core Business, Closing) — one LLM call for all four, stored in `feedback.phase_language`, rendered as its own block **under** the Kennzahlen. It is deliberately prose and not a Measurement (ADR 0056): the observation is a change over the call, which no single figure carries and which would need the norms ADR 0051 declined to invent. The `phase_appropriate_language` entry in `metrics.py` therefore stays inactive forever. The peak-end rule is applied as **text weight** — the closing gets more of the paragraph and first claim on the suggestion — never as a score, since there is none (ADR 0004). The Session row is written under the caller's Keycloak `sub` (ADR 0009/0031), handed to `persist_session` straight from the handshake. `Measurement`/`Finding` hang off the `Session`. `Finding` has no writer and no reader — the table stays for pilot data, but nothing in the API, the prompt or the frontend refers to it. `GET /api/sessions` is the per-user history (ADR 0064, F-13/F-48): the caller's own Sessions, newest first, paginated (default 20, max 100), with each Session's Measurements but **without** their `detail_json` (the loudness curve would dwarf the payload) and without the wrap-up *text*, which stays on the detail route — it does carry `has_feedback` and `feedback_status`, so the history can say per row whether there is a wrap-up to open, one still being generated, or none coming. Ownership is the `WHERE` clause, not a check on the result — a foreign Session is never a candidate, so the 404-vs-403 question does not arise here; `session.subject_id` is indexed for exactly this query and is the one indexed non-foreign-key column in the schema (migration `18f5098dfb1b`, which takes up the exception ADR 0052 named). Note the collision: `status` means `session.status` (`completed`/`aborted`) on the listing and the *feedback job* status on the detail route. There is still no shareable route — a wrap-up is reachable to its owner and to nobody else. The detail route also carries `follow_up` — the card of the *Folgeszenario* the worker wrote from this Session (F-60, above), or null. The post-call screen shows it under the improvement points with two buttons: **Bearbeiten** opens the ordinary editor on the stored row, **Starten** goes straight into the call against the same Persona this training was played with — hence `persona_id` beside `persona` on the detail route, since `session.start` takes ids (ADR 0050); a *different* partner means starting the row from the setup screen instead. While it is still being written there is one busy line in the same place, driven by the wrap-up's own poll: `useSessionFeedback` keeps polling past the wrap-up until the follow-up lands or a shorter grace period expires, so there is no second poller. `FeedbackReport` takes that block as an optional prop because the two screens that show it differ: **`PastSessionView` shows it too**, minus the waiting (nothing is in flight there, so `pending` is false and a Session with no follow-up shows no block), with the editor rendered over that page and **Starten** handing the pairing to the training flow through the router's location state (`TrainingStart` in `routes.ts`, consumed once and cleared so a reload or Back cannot start a second call). The setup screen's category is the third way back to an older follow-up. What the progress view may *show* is constrained by ADR 0065: values over time, yes; target bands, good/bad colour, improvement arrows or any cross-Session score, no, on the same grounds as ADR 0004/0051. **That view is built (F-13, `docs/dashboard-konzept.md`, stage 1 of 3)**: `/fortschritt` (`ProgressView.tsx`) plus the per-metric level `/fortschritt/:metricKey` (`ProgressMetricView.tsx`, whose table is the accessible half of the chart and not a fallback for it); the third level is the existing `PastSessionView`. It runs at the app's full width (`app-page-wide`, 1440px, with `AppLayout wide` widening the header to match so the two align) and adds **no endpoint** — `GET /api/sessions` already carries each Session's Measurements, and an aggregate route would be a second path to the same numbers; two charts carry the screen while little has been measured, both needing only the session rows: `ActivityChart.tsx` (trainings per day/week/month, abandoned ones as a lighter share of the same hue, never red) and `VarietyGrid.tsx` (Scenario × Persona, *played combinations only* — a full-library grid with empty cells would turn a description into a homework list), plus call length as a derived series beside the measured ones; `utils/progressStats.ts` does the grouping, the own-median-plus-MAD band (the same construction `metrics.py` uses for the loudness course, and the only reference point ADR 0051 allows) and the `MIN_SESSIONS_FOR_SERIES` = 3 rule that shows single values instead of a two-point line. Focus goals (F-61) drive the top block: `utils/focusMetrics.ts` maps each goal to the Kennzahlen behind it, and a goal with none says so rather than rendering an empty tile — 8 of the 15 are measurable today, 2 are answered by activity figures, 5 only by wrap-up text. No focus goals means that block is *replaced* by the three most-varying metrics plus an invitation, never left empty. The recurring-strengths/weaknesses block and the practice suggestion are laid out but explicitly labelled **Beispiel** (`ProgressPreview.tsx`): `feedback_point` carries no goal tag, so nothing can be counted across Sessions yet, and inventing a plausible weakness under someone's own name is the one thing this screen must not do. Building it surfaced an old defect: `metric_type` still held the pre-ADR-0057 German keys *active* beside their English replacements (same display name, so a renamed metric would have drawn two identical charts) because `provision.py` never applied `_deactivate_missing` to MetricType although ADR 0057 says it does. Fixed there, plus `active` on the listing's measurements so the dashboard drops retired ones; the *detail* route deliberately does not filter, since a past Session should show what was measured then. Merging old and new keys was rejected: ADR 0051 changed the definitions, and splicing two different measurements into one line is the quiet kind of wrong. Self-service deletion **is** built (ADR 0066): withdrawing consent removes everything, `DELETE /api/sessions/{extern_id}` removes one training, and both go through `backend/deletion.py`. Because `session_scope()` is synchronous, database calls from the async Session path go through `asyncio.to_thread`, and FastAPI's sync `def` endpoints get the same effect from its threadpool; nothing blocking may run on the event loop that streams live audio.

## Build / Run

- Frontend: `cd frontend && npm install && npm run build` (writes to `frontend/dist`, which the backend serves). The Vite dev server (`npm run dev`) is not a supported workflow — it has no backend URL configured (there is no `VITE_API_URL` anymore; the app is always run via Docker) and VAD is broken under it anyway (see next bullet). CORS in `backend/app.py` still allows `http://localhost:5173` but nothing depends on it.
- Turn-taking uses Silero VAD in-browser (`@ricky0123/vad-web` + `onnxruntime-web`, ONNX+WASM); `npm run dev`/`npm run build`'s `predev`/`prebuild` hooks (`frontend/scripts/copy-vad-assets.mjs`) copy its ~15MB of runtime assets into `frontend/public/vad/` (gitignored, regenerated on every dev/build run — not tied to `npm install`, since the Docker build's `npm ci` layer runs before the rest of the source, including this script, is even copied into the image). Known gap: this currently fails under `npm run dev` specifically — Vite 5's dev-server import-analysis 500s on onnxruntime-web's dynamically-imported `.mjs` WASM glue (a dev-only Vite/onnxruntime-web interaction, unresolved so far). The production build (`npm run build`, served by the backend) is unaffected — use that path when testing VAD/turn-taking changes.
- Local backend: `uvicorn backend.app:app --reload`
- Docker: `docker compose up --build` (builds the frontend too, via a multi-stage Dockerfile; serves on `http://localhost:8391` — a deliberately non-standard host port, mapped to the container's 8000, set in `compose.yaml`). Add `--watch` to pick up code changes automatically (`develop.watch` in `compose.yaml`): backend edits are synced into the running container and the app restarted, without a full rebuild; frontend edits and `requirements.txt` changes trigger a rebuild instead. To restart from scratch: `docker compose down` → `docker compose build` (add `--no-cache` if a frontend change is not showing up) → `docker compose up`. Postgres and the Keycloak session survive that. To re-import `keycloak/direkt-realm.json`, also drop the Keycloak volume first (`docker volume rm direkt-calltrainer-keycloak-data`) — Keycloak then mints fresh signing keys, invalidating the browser session, but `apiFetch` catches the resulting 401 and redirects to login. `docker compose down -v` wipes Postgres too. The Python base image is **pinned to 3.12**, not `python:3-slim`: that floating tag had already moved to 3.14, where SQLAlchemy 2.0.36 cannot resolve the `Mapped[int | None]` annotations and every database import dies.
- `LOG_TRANSCRIPTS` (in `.env`, default off) writes the spoken content of every call into the log file. Leave it off outside local debugging — no deletion path reaches that file (ADR 0066), so a transcript written there outlives a withdrawn consent and a deleted training. The app logs a warning at boot while it is on.
- Copy `.env.example` to `.env` and fill in real values before running — `.env` is gitignored and read via `env_file` in the compose file, and by Vite (`envDir` at the repo root) for the `VITE_OIDC_*` build vars.
- Keycloak (ADR 0009): `docker compose up` starts a local Keycloak on `http://localhost:18081` and imports `keycloak/direkt-realm.json` (client `calltrainer-frontend`, dev users `alice`/`bob`/`carol`, password = username). Each dev user carries a `tenant` attribute (`alice`/`bob` → `solox`, `carol` → `appollo`) that the `calltrainer tenant` protocol mapper puts in the token, so they resolve to those tenants (ADR 0060). The realm's user profile sets `unmanagedAttributePolicy: ENABLED` so that custom `tenant` attribute survives import. Each dev user's `id` is pinned in the JSON, so a re-import keeps the same `sub` and authored Scenarios (`scenario.created_by`, ADR 0058) are not orphaned — Keycloak's realm JSON rejects unknown keys, so that rationale lives here, not in a comment field. Edit the JSON → wipe the volume to re-import: `docker compose down -v` (or `docker volume rm direkt-calltrainer-keycloak-data`). `KC_HOSTNAME` pins the token issuer to `localhost:18081`; the app container reaches the realm's keys over the compose network via `OIDC_JWKS_URL` (`backend/auth.py`). Keycloak admin console: `admin`/`admin`. For a host-only `uvicorn` run, point `OIDC_ISSUER` at the same URL and drop `OIDC_JWKS_URL` (the host can reach `localhost:18081` directly).
- There is no LLM mock any more — `scripts/mock_llm_server.py` was removed in commit 113394f and never replaced, so anything touching STT/LLM/TTS needs a reachable `DIREKT_URL`. To exercise the wrap-up generator without one, stub `backend.clients.llm.complete`.
- Checking the pipeline backends: `python scripts/check_backends.py` fires one minimal real request at each configured STT/LLM/TTS backend and logs OK/FAIL per step (exit 0 only if all pass); it respects the `DEBUG` toggle (forces the TTS check onto the DiReKT fallback instead of KugelAudio). The app runs the same check (`backend/clients/health.py:check_backends`) at startup from the `lifespan` handler — a dead model is logged as `Startup check: <STEP> FAILED` but does not stop the app from booting.
- Every compose service carries `restart: unless-stopped`. Without it a Docker restart or a crash leaves a container down, and on the **worker** that is silent — calls keep working and wrap-ups simply never appear, which is exactly how a dead worker went unnoticed for hours. Note also that `docker compose up -d app` does *not* start the worker (it is not in app's `depends_on`); use a bare `docker compose up -d`. If wrap-ups are missing, `docker compose ps -a` first.
- Retention: `python scripts/apply_retention.py` lists what is past the six-month period, `--apply` deletes it. Works from a host shell (no Redis needed). The app sweeps daily by itself; this is for checking the period before it bites or clearing a backlog after downtime.
- Wrap-ups can be regenerated: `docker compose exec app python scripts/requeue_feedback.py [--apply]` re-queues every stored Session that has Turns but no Feedback. Nothing is regenerated from audio — the wrap-up is written from the stored Transcript and Measurements (ADR 0049), so a Session from days ago can still be analysed. The job also writes the Folgeszenario (ADR 0069), but a re-run cannot produce a second one: `scenario.derived_from_session_id` is UNIQUE. Must run inside the container: Redis is not published to the host.
- Feedback worker: `docker compose up` now also starts `redis` and a `worker` service running `python -m backend.worker`. The worker shares the app's image and database but no request cycle; if it is down, calls still work and wrap-ups simply queue. RQ forks per job, so the worker only runs on Linux — use the container, not a host process, on Windows.
- Database: the app migrates to head and seeds the reference tables itself at startup (`backend/db/provision.py`, called from the `lifespan` handler), so `docker compose up` needs no manual step — a provisioning failure is logged as `Database provisioning failed` and does not stop the app, but the setup endpoints then serve nothing and every Session fails to persist. To do it by hand against a host-side database, `docker compose up -d db` then `python scripts/seed_reference_data.py`, which is a thin CLI over the same `provision()`. The seed script calls `load_dotenv()` itself; `backend/db/session.py` does not — it assembles the connection URL in `build_database_url()` lazily, on the first call to `session_scope()`/`get_engine()`, so importing it never requires an environment. There is **no `DATABASE_URL`**: the URL is built from `POSTGRES_USER`/`POSTGRES_PASSWORD`/`POSTGRES_DB` plus an optional `POSTGRES_HOST`/`POSTGRES_PORT`, which default to `localhost:5432` for host-side calls — one place for the password instead of a URL duplicated across `.env` and `compose.yaml`. Alembic uses the same function, so migrations can never run against a different database than the app; the app and worker containers get `POSTGRES_HOST=db` from `compose.yaml`, which is the only part that differs. Provisioning takes a Postgres advisory lock (`PROVISION_LOCK_KEY` and the `advisory_lock()` context manager in `backend/db/session.py`) twice in sequence, never nested: once in `migrations/env.py` around the migration and once in `provision.py` around the seeding, each on a connection of its own. That is what keeps the app and the worker starting at once from applying the same revision twice *and* from racing `_upsert` into a duplicate-key rollback that would log as `Database provisioning failed`. Do not hold it across both steps — the process would wait on itself, without a timeout.
- Schema changes: edit `backend/db/models.py`, then `alembic revision --autogenerate -m "..."`. Constraint and index names come from the naming convention on `Base.metadata` (`backend/db/base.py`, ADR 0053) — never name one by hand, and never remove the convention: without it autogenerate emits unnamed constraints whose `downgrade()` cannot run. Note that `op.create_check_constraint`/`op.drop_constraint` apply that convention *themselves*, so a migration passes the bare name (`status_valid`), never the prefixed one. Every foreign-key column carries `index=True` (ADR 0052); two tests enforce both rules. Alembic does **not** autodetect `CHECK` constraints — those have to be written into the migration by hand. **Always read the generated migration before applying it** — autogenerate adds `NOT NULL` columns without backfilling, which fails on non-empty tables, and it cannot recognise a rename: it emits a drop plus a create, which would destroy stored Sessions. The ER diagram is regenerated automatically on every docs build (see below); `python scripts/generate_erd.py` refreshes `docs/er_modell.png`/`.svg` on demand and needs the Graphviz `dot` binary (`brew install graphviz`). Three invariants the database enforces since migration `a7c39e5f21b8`, to be kept in `models.py` and in any migration that touches these tables: `measurement` is unique per (`session_id`, `metric_type_id`) and `turn` per (`session_id`, `seq_index`) — one set of statistics per Session (ADR 0051), and a transcript order that does not depend on the server; foreign keys into the reference tables (`persona`, `scenario`, `language`, `metric_type`) carry **no** `ondelete` at all, the nullable ones included — only back-references into rows the Session owns (`feedback_point.turn_id`/`finding_id`) are `SET NULL`; and every timestamp column is `DateTime(timezone=True)` and written exclusively with `datetime.now(UTC)`, never a naive `datetime.now()`, because Postgres would read a naive value in the server's zone and every stored time would shift if the app container's `TZ` ever differed. Column defaults (`active`, `attempts`, `extern_id`) are Python-side only, no `server_default`, so a row inserted from `psql` has to name them.
- Docs site (arc42 + ADRs): `mkdocs serve` (serves on `http://localhost:8000`; the app is on `8391` now, so no clash). `mkdocs build` writes static output to `site/` (gitignored).

- Tests: `pip install -r requirements.txt` then `pytest` (config in `pytest.ini`, suite in `tests/`). Feature-traceable backend tests — every file cites the `F-xx`/`R-xx`/ADR it proves; see `tests/README.md` for the traceability matrix. Two kinds live side by side. Most need no network, database, credentials or browser: the STT/LLM/TTS pipeline backends are faked in `tests/conftest.py`, the REST layer runs over an in-process ASGI transport, and `conftest.py` claims the `POSTGRES_*` names with deliberately unusable values *before* the backend is imported, so a test that does not ask for a database cannot reach the real one by accident — `backend/clients/config.py` calls `load_dotenv()` on import, which would otherwise put the developer's real settings into the environment for the whole session. `tests/test_database_isolation.py` guards that ordering. The persistence tests each create their own throwaway database on the server from `.env`, migrate it and drop it afterwards — so Postgres has to be running (`docker compose up -d db`), but the development database is never touched; without a reachable server they skip rather than fail. They cover the migration chain in both directions, the naming convention and the FK indexes, seed idempotency and deactivation (and that a deactivated row leaves the setup endpoints), the Session write path, the setup and session endpoints including the ownership check, the wrap-up job's status lifecycle, the unique and undeletable invariants above, and that deleting a Session removes its subtree by ORM and by raw SQL while leaving reference data alone.
- Frontend tests: `cd frontend && npm test` (Vitest, `vitest run`). Deliberately narrow — not a general component-test setup. It covers only the live-call audio path: the barge-in races in `useStreamedAudioPlayback` and `useSessionSocket`, which `tsc` cannot see and which are near-impossible to catch by hand. jsdom plus hand-written Web Audio / WebSocket fakes (`frontend/src/test/setup.ts`) that let a test drive decode timing and socket delivery frame by frame; no network, no browser. The specs are excluded from the production build's type-check (`tsconfig.json`), so they are checked only by esbuild when they run.
- Lint: `flake8 .` and `PYTHONPATH=. pylint backend/ scripts/ tests/`. Both are clean (pylint 10.00) and should stay that way — a deliberate exception carries an inline `# pylint: disable=X  # reason`. `PYTHONPATH=.` is required — without it pylint cannot resolve the `backend.*` imports and reports nothing but import errors. Alembic revisions are excluded from both (their formatting comes from autogenerate and would be rewritten on every new revision) — via `ignore-paths`/`per-file-ignores` patterns written to match even when an editor lints one by its absolute path.
