# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Calltrainer is an AI-powered phone conversation trainer that provides real-time analysis and behavioral feedback during simulated calls (from README.md).

## Current State

FastAPI backend (`backend/app.py`) serves the API and, once built, the React + TypeScript frontend (`frontend/`, built with Vite; the backend serves `frontend/dist`). `/health` is liveness only (touches nothing, so a brief database outage cannot look like a dead process) and `/health/ready` is readiness (checks the database) — the compose healthcheck asks the latter, because an instance that cannot reach Postgres can only answer 503. `/api/personas` and `/api/scenarios` list the Persona/Scenario options shown before a Session starts — any Persona can run any Scenario, no compatibility to filter by. **Both read from the `persona`/`scenario` tables, not from Python lists** (ADR 0041), and serve only rows with `active` set: `backend/personas.py` and `backend/scenarios.py` still hold the dataclasses, but their `PERSONAS`/`SCENARIOS` lists are now only input for the seed, because ADR 0024 has Users authoring their own. Rows dropped from the seed are deactivated rather than deleted — `session` references them by foreign key, so a past Session has to stay readable. Auth is Keycloak/OIDC (ADR 0009, now built): the SPA logs in with PKCE against the `direkt` realm (`calltrainer-frontend` client), `backend/auth.py` verifies the bearer JWT (`OIDC_ISSUER`, audience `calltrainer`) on `/api/personas`, `/api/scenarios`, `/api/sessions/{id}` and the `/ws/session` handshake — the WebSocket carries the token in its `session.start` message since a browser can't set a header on it. `/health`, `/health/ready` and the static frontend stay open. No role checks. `docker compose up` brings its own Keycloak on `:18081` (`keycloak/direkt-realm.json`, dev users alice/bob/carol). There is no Language selection: each Persona has exactly one fixed Language/voice (stored on the `persona` row — `language_code`, `tts_voice`, `kugelaudio_voice_id`), and only German is supported for now (English support was removed, not just hidden — re-introducing it means giving the relevant Personas their own language and voice, not a shared global setting). The live Session itself runs over a per-Session WebSocket at `/ws/session` (`backend/api/session_ws.py`): the client streams one full Turn of recorded audio at a time (browser-side voice-activity detection ends each Turn automatically, no manual button) and the user can talk over the persona to cut a reply short (barge-in, ADR 0035); the server runs each Turn through STT → streamed dialogue generation → chunked TTS (`backend/session/orchestrator.py`, `backend/clients/`), and streams synthesized audio back chunk-by-chunk so playback can start before the full reply is done generating (ADR 0033, which supersedes the earlier non-streaming pipeline; ADR 0044 refines the TTS leg — each chunk is forwarded to the client sub-chunk by sub-chunk as KugelAudio's `stream_async` produces it, not buffered). STT and LLM call the same OpenAI-compatible DiReKT model gateway, configured via a single `.env` base URL/key pair (`DIREKT_URL`, `DIREKT_API_KEY`) plus one model name per step (`STT_MODEL`, `LLM_MODEL`) — neither has a fallback. TTS defaults to KugelAudio (a separate SDK, not an HTTP endpoint on the DiReKT gateway; `KUGELAUDIO_API_KEY`/`KUGELAUDIO_MODEL`), falling back to the DiReKT TTS model (`TTS_MODEL`) if KugelAudio fails, or always if `DEBUG=True` is set (`backend/clients/config.py`). No text is shown during the live call, only a state animation (listening/thinking/speaking) — the full Transcript is sent once, at the end, and shown as a post-call summary. Persistence lives in `backend/db/`: `models.py` holds the SQLAlchemy schema, `base.py` the declarative base carrying the constraint naming convention, `session.py` the `session_scope()` context manager used for all database access (it assembles the connection URL from the `POSTGRES_*` settings, lazily), `migrations/` the Alembic revisions, and `provision.py` the migrate-and-seed step the app runs at startup. Postgres runs as the `db` service in `compose.yaml` (ADR 0010). The backend test suite lives in `tests/` (pytest, feature-traceable — see the Tests section under Build / Run); the frontend has no JS test runner. `docs/arc42.md` is filled in.

**Table and column names are English throughout (ADR 0026), but the wire stays German.** The schema says `turn.speaker` in `('user','persona')` and `feedback_point.kind` in `('strength','improvement')`; the JSON the frontend reads says `sprecher` in `('nutzer','persona')` and `art` in `('staerke','verbesserung')`, exactly as `frontend/src/protocol.ts` declares. `backend/api/sessions.py` is the boundary that translates back, `session/persistence.py` and `feedback/generator.py` translate in — a rename on that boundary is a frontend change, not a backend one. German also remains in user-facing content (Persona/Scenario text, metric display names, the wrap-up prompt) and in the documentation. Every constraint and index name comes from the naming convention on `Base.metadata` (ADR 0053), every foreign-key column is indexed (ADR 0052), and ownership edges carry `ON DELETE CASCADE` with `passive_deletes=True` on the ORM side, so deleting a Session removes its subtree by raw SQL as well as through the ORM, while reference tables deliberately do not cascade. Vocabularies (`session.status`, `turn.speaker`, `feedback_point.kind`, `analysis_job.kind`/`status`) are enforced by CHECK constraints rather than Postgres ENUMs. `session.extern_id` is the unguessable UUID the client sees (ADR 0050); the primary key stays internal. The migrations and the ER diagram in `docs/datenmodell.md` are generated from `models.py`, not edited by hand; the schema's rationale is in ADRs 0025 through 0032, 0050, 0052 and 0053.

Post-call analysis lives in `backend/feedback/` and produces **one set of statistics per Session, never per Turn** (ADR 0051): F-53's Kennzahlen — Redeanteil, Fragen, Sprechtempo, Wortanzahl, Reaktionszeit, Sprechpausen — plus F-37's loudness curve. `acoustics.py` is the only module that imports `parselmouth`; it measures one Turn's audio inline in the live path and returns raw, concatenable facts (ADR 0047/0048). `metrics.py` owns the metric inventory, which `provision.py` also seeds, so the two cannot drift — adding a metric is one `MetricDef`. Its metric *keys* stay German (`redeanteil`, `tempo`, `lautstaerke`), because they travel to the frontend as `schluessel`. **No metric carries a target range**: none is validated for this population, and an invented threshold is a score in disguise (ADR 0004/0051), so nothing writes `Finding` rows and the wrap-up prompt forbids judging a figure against a norm. **Nothing in the Feedback is measured against the Persona** either — it is a synthesized voice, so comparing the user to it would report a TTS setting as if it described the user (ADR 0051). `session/models.py` owns the Turn timeline: a Turn is one exchange in memory, but `utterances()` flattens it to one row per speaker for storage, which is what gives every line its own offset and makes the Gesprächsprotokoll timestamped; `conversation()` folds the call for `metrics`. Each speaker's speaking window is tracked separately so the gateway's latency is charged to neither: Reaktionszeit runs from when the Persona stopped speaking, and the Session clock starts at the client's `session.activate`, not at connect. `persistence.py` writes it all in one transaction after the call has ended, never during it (ADR 0034) — a Session the client abandoned mid-call is deliberately not persisted, and a database failure is logged but never fatal, since the Transcript is already in memory and gets sent either way. `generator.py` produces the wrap-up in the RQ worker (ADR 0049), and `GET /api/sessions/{extern_id}` (ADR 0050, behind the same bearer token as the rest of `/api`) serves it to the post-call screen, which polls (`useSessionFeedback`, `FeedbackView`). The Session row is written under the caller's Keycloak `sub` (ADR 0009/0031), handed to `persist_session` straight from the handshake. `Measurement`/`Finding` hang off the `Session`. `Finding` has no writer and no reader — the table stays for pilot data, but nothing in the API, the prompt or the frontend refers to it. There is deliberately **no listing endpoint** and no shareable route: the wrap-up is reachable for as long as that screen is, plus a `sessionStorage` entry so a reload does not discard it. Because `session_scope()` is synchronous, database calls from the async Session path go through `asyncio.to_thread`, and FastAPI's sync `def` endpoints get the same effect from its threadpool; nothing blocking may run on the event loop that streams live audio.

## Build / Run

- Frontend: `cd frontend && npm install && npm run build` (writes to `frontend/dist`, which the backend serves). The Vite dev server (`npm run dev`) is not a supported workflow — it has no backend URL configured (there is no `VITE_API_URL` anymore; the app is always run via Docker) and VAD is broken under it anyway (see next bullet). CORS in `backend/app.py` still allows `http://localhost:5173` but nothing depends on it.
- Turn-taking uses Silero VAD in-browser (`@ricky0123/vad-web` + `onnxruntime-web`, ONNX+WASM); `npm run dev`/`npm run build`'s `predev`/`prebuild` hooks (`frontend/scripts/copy-vad-assets.mjs`) copy its ~15MB of runtime assets into `frontend/public/vad/` (gitignored, regenerated on every dev/build run — not tied to `npm install`, since the Docker build's `npm ci` layer runs before the rest of the source, including this script, is even copied into the image). Known gap: this currently fails under `npm run dev` specifically — Vite 5's dev-server import-analysis 500s on onnxruntime-web's dynamically-imported `.mjs` WASM glue (a dev-only Vite/onnxruntime-web interaction, unresolved so far). The production build (`npm run build`, served by the backend) is unaffected — use that path when testing VAD/turn-taking changes.
- Local backend: `uvicorn backend.app:app --reload`
- Docker: `docker compose up --build` (builds the frontend too, via a multi-stage Dockerfile; serves on `http://localhost:8391` — a deliberately non-standard host port, mapped to the container's 8000, set in `compose.yaml`). Add `--watch` to pick up code changes automatically (`develop.watch` in `compose.yaml`): backend edits are synced into the running container and the app restarted, without a full rebuild; frontend edits and `requirements.txt` changes trigger a rebuild instead. The Python base image is **pinned to 3.12**, not `python:3-slim`: that floating tag had already moved to 3.14, where SQLAlchemy 2.0.36 cannot resolve the `Mapped[int | None]` annotations and every database import dies.
- Copy `.env.example` to `.env` and fill in real values before running — `.env` is gitignored and read via `env_file` in the compose file, and by Vite (`envDir` at the repo root) for the `VITE_OIDC_*` build vars.
- Keycloak (ADR 0009): `docker compose up` starts a local Keycloak on `http://localhost:18081` and imports `keycloak/direkt-realm.json` (client `calltrainer-frontend`, dev users `alice`/`bob`/`carol`, password = username). Edit the JSON → wipe the volume to re-import: `docker compose down -v` (or `docker volume rm direkt-calltrainer-keycloak-data`). `KC_HOSTNAME` pins the token issuer to `localhost:18081`; the app container reaches the realm's keys over the compose network via `OIDC_JWKS_URL` (`backend/auth.py`). Keycloak admin console: `admin`/`admin`. For a host-only `uvicorn` run, point `OIDC_ISSUER` at the same URL and drop `OIDC_JWKS_URL` (the host can reach `localhost:18081` directly).
- There is no LLM mock any more — `scripts/mock_llm_server.py` was removed in commit 113394f and never replaced, so anything touching STT/LLM/TTS needs a reachable `DIREKT_URL`. To exercise the wrap-up generator without one, stub `backend.clients.llm.complete`.
- Checking the pipeline backends: `python scripts/check_backends.py` fires one minimal real request at each configured STT/LLM/TTS backend and logs OK/FAIL per step (exit 0 only if all pass); it respects the `DEBUG` toggle (forces the TTS check onto the DiReKT fallback instead of KugelAudio). The app runs the same check (`backend/clients/health.py:check_backends`) at startup from the `lifespan` handler — a dead model is logged as `Startup check: <STEP> FAILED` but does not stop the app from booting.
- Feedback worker: `docker compose up` now also starts `redis` and a `worker` service running `python -m backend.worker`. The worker shares the app's image and database but no request cycle; if it is down, calls still work and wrap-ups simply queue. RQ forks per job, so the worker only runs on Linux — use the container, not a host process, on Windows.
- Database: the app migrates to head and seeds the reference tables itself at startup (`backend/db/provision.py`, called from the `lifespan` handler), so `docker compose up` needs no manual step — a provisioning failure is logged as `Database provisioning failed` and does not stop the app, but the setup endpoints then serve nothing and every Session fails to persist. To do it by hand against a host-side database, `docker compose up -d db` then `python scripts/seed_reference_data.py`, which is a thin CLI over the same `provision()`. The seed script calls `load_dotenv()` itself; `backend/db/session.py` does not — it assembles the connection URL in `build_database_url()` lazily, on the first call to `session_scope()`/`get_engine()`, so importing it never requires an environment. There is **no `DATABASE_URL`**: the URL is built from `POSTGRES_USER`/`POSTGRES_PASSWORD`/`POSTGRES_DB` plus an optional `POSTGRES_HOST`/`POSTGRES_PORT`, which default to `localhost:5432` for host-side calls — one place for the password instead of a URL duplicated across `.env` and `compose.yaml`. Alembic uses the same function, so migrations can never run against a different database than the app; the app and worker containers get `POSTGRES_HOST=db` from `compose.yaml`, which is the only part that differs. Migrations take a Postgres advisory lock (`backend/db/migrations/env.py`), so the app and the worker starting at once cannot apply the same revision twice.
- Schema changes: edit `backend/db/models.py`, then `alembic revision --autogenerate -m "..."`. Constraint and index names come from the naming convention on `Base.metadata` (`backend/db/base.py`, ADR 0053) — never name one by hand, and never remove the convention: without it autogenerate emits unnamed constraints whose `downgrade()` cannot run. Note that `op.create_check_constraint`/`op.drop_constraint` apply that convention *themselves*, so a migration passes the bare name (`status_valid`), never the prefixed one. Every foreign-key column carries `index=True` (ADR 0052); two tests enforce both rules. Alembic does **not** autodetect `CHECK` constraints — those have to be written into the migration by hand. **Always read the generated migration before applying it** — autogenerate adds `NOT NULL` columns without backfilling, which fails on non-empty tables, and it cannot recognise a rename: it emits a drop plus a create, which would destroy stored Sessions. The ER diagram is regenerated automatically on every docs build (see below); `python scripts/generate_erd.py` refreshes `docs/er_modell.png`/`.svg` on demand and needs the Graphviz `dot` binary (`brew install graphviz`).
- Docs site (arc42 + ADRs): `mkdocs serve` (serves on `http://localhost:8000`; the app is on `8391` now, so no clash). `mkdocs build` writes static output to `site/` (gitignored).

- Tests: `pip install -r requirements.txt` then `pytest` (config in `pytest.ini`, suite in `tests/`). Feature-traceable backend tests — every file cites the `F-xx`/`R-xx`/ADR it proves; see `tests/README.md` for the traceability matrix. Two kinds live side by side. Most need no network, database, credentials or browser: the STT/LLM/TTS pipeline backends are faked in `tests/conftest.py`, the REST layer runs over an in-process ASGI transport, and `conftest.py` claims the `POSTGRES_*` names with deliberately unusable values *before* the backend is imported, so a test that does not ask for a database cannot reach the real one by accident — `backend/clients/config.py` calls `load_dotenv()` on import, which would otherwise put the developer's real settings into the environment for the whole session. `tests/test_database_isolation.py` guards that ordering. The persistence tests each create their own throwaway database on the server from `.env`, migrate it and drop it afterwards — so Postgres has to be running (`docker compose up -d db`), but the development database is never touched; without a reachable server they skip rather than fail. They cover the migration chain in both directions, the naming convention and the FK indexes, seed idempotency and deactivation, the Session write path, the setup and session endpoints, and that deleting a Session removes its subtree by ORM and by raw SQL while leaving reference data alone. Frontend has no JS test runner configured.
- Lint: `flake8 .` and `PYTHONPATH=. pylint backend/ scripts/ tests/`. `flake8` is clean and should stay that way; `pylint` currently scores ~9.9 with a handful of pre-existing findings in `session_ws.py`, `orchestrator.py` and `scripts/seed_reference_data.py`. `PYTHONPATH=.` is required — without it pylint cannot resolve the `backend.*` imports and reports nothing but import errors. Alembic revisions are excluded from both (their formatting comes from autogenerate and would be rewritten on every new revision).
