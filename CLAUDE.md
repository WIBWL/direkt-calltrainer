# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Calltrainer is an AI-powered phone conversation trainer that provides real-time analysis and behavioral feedback during simulated calls (from README.md).

## Current State

FastAPI backend (`backend/app.py`) serves the API and, once built, the React + TypeScript frontend (`frontend/`, built with Vite; the backend serves `frontend/dist`). `/health` is liveness only (touches nothing) and `/health/ready` is readiness (checks the database) — the compose healthcheck asks the latter, because an instance that cannot reach Postgres can only answer 503; `/api/personas` and `/api/scenarios` list the Persona/Scenario options shown before a Session starts — any Persona can run any Scenario, no compatibility to filter by. **Both read from the database, not from Python lists**, so the app needs a migrated and seeded Postgres to serve anything (they return 503 without one). `backend/personas.py` and `backend/scenarios.py` still hold the dataclasses, but their `PERSONAS`/`SCENARIOS` lists are now only input for `scripts/seed_reference_data.py`; the `persona`/`scenario` tables are the source of truth, because ADR 0024 has Users authoring their own. Rows dropped from the seed are deactivated rather than deleted — `session` references them by foreign key. There is no Language selection: each Persona has exactly one fixed Language/voice (stored on the `persona` row), and only German is supported for now (English support was removed, not just hidden — re-introducing it means giving the relevant Personas their own `language_id`/`language_name`/voice, not a shared global setting). The live Session itself runs over a per-Session WebSocket at `/ws/session` (`backend/api/session_ws.py`): the client streams one full Turn of recorded audio at a time (browser-side voice-activity detection ends each Turn automatically, no manual button), the server runs it through STT → streamed dialogue generation → chunked TTS (`backend/session/orchestrator.py`, `backend/clients/`), and streams synthesized audio back chunk-by-chunk so playback can start before the full reply is done generating (ADR 0033, which supersedes the earlier non-streaming pipeline). All three steps call the same university-hosted, OpenAI-compatible `efre-direkt` endpoint, configured via a single `.env` base URL/key pair (`EFRE_URL`, `EFRE_API_KEY`) plus one model name per step (`STT_MODEL`, `LLM_MODEL`, `TTS_MODEL`). No text is shown during the live call, only a state animation (listening/thinking/speaking) — the full Transcript is sent once, at the end, and shown as a post-call summary. Persistence lives in `backend/db/`: `models.py` holds the SQLAlchemy schema, `session.py` the `session_scope()` context manager used for all database access, `repository.py` the read functions that map ORM rows onto the plain dataclasses the rest of the backend uses (so neither the API layer nor the orchestrator touches ORM objects), and `migrations/` the Alembic revisions; Postgres runs as the `db` service in `compose.yaml` (ADR 0010). A finished Session is written once, after it ends (ADR 0034): `session_ws.py` calls `repository.save_session()` via `asyncio.to_thread` after the last Turn, never during the call. A Session the client abandoned mid-call is deliberately not persisted, and a database failure is logged but never fatal — the Transcript is already in memory and gets sent either way. `session.extern_id` is the UUID the client sees; the primary key stays internal. `subject_id` is a **fresh random UUID per Session** — a pseudonym, not an anonymisation (the Transcript can still identify a person), deliberately not reused so Sessions stay unlinkable while there is no account to attach them to. `GET /api/sessions/{extern_id}` reads one stored Session back, with a `transcript` in the same shape the WebSocket sends in `session.ended`, so one view renders both a live and a reloaded Session. There is deliberately **no listing endpoint**: because `subject_id` is a per-Session pseudonym, the server cannot tell which Sessions belong to the same person — only a client that kept its ids can. The analysis subtree (`Measurement`, `Finding`, `Feedback`, `FeedbackPoint`, `AnalysisJob`) still has no writer. Table and column names are English throughout (ADR 0026); German remains only in user-facing content and in the documentation. Because `session_scope()` is synchronous, database calls from the async Session path go through `asyncio.to_thread`, and FastAPI's sync `def` endpoints get the same effect from its threadpool; nothing blocking may run on the event loop that streams live audio. The migrations and the ER diagram in `docs/datenmodell.md` are generated from `backend/db/models.py`, not edited by hand. The schema's rationale is in the persistence ADRs 0025 through 0032, its storage policy in ADR 0034. There is no AI-generated Feedback (ADR 0004/0014/0018/0019's async worker is not built). `docs/arc42.md` is filled in.

## Build / Run

- Frontend: `cd frontend && npm install && npm run build` (writes to `frontend/dist`, which the backend serves) or `npm run dev` (Vite dev server on `http://localhost:5173`, calls the backend cross-origin via `VITE_API_URL`; the backend allows this origin via CORS)
- Turn-taking uses Silero VAD in-browser (`@ricky0123/vad-web` + `onnxruntime-web`, ONNX+WASM); `npm run dev`/`npm run build`'s `predev`/`prebuild` hooks (`frontend/scripts/copy-vad-assets.mjs`) copy its ~15MB of runtime assets into `frontend/public/vad/` (gitignored, regenerated on every dev/build run — not tied to `npm install`, since the Docker build's `npm ci` layer runs before the rest of the source, including this script, is even copied into the image). Known gap: this currently fails under `npm run dev` specifically — Vite 5's dev-server import-analysis 500s on onnxruntime-web's dynamically-imported `.mjs` WASM glue (a dev-only Vite/onnxruntime-web interaction, unresolved so far). The production build (`npm run build`, served by the backend) is unaffected — use that path when testing VAD/turn-taking changes.
- Local backend: `uvicorn backend.app:app --reload`
- Docker: `docker compose up --build` (builds the frontend too, via a multi-stage Dockerfile; serves on `http://localhost:8000`). `docker-entrypoint.sh` runs `alembic upgrade head` and the seed before the app starts — both are required, since the setup endpoints read from the database. The Python base image is **pinned to 3.12**, not `python:3-slim`: that floating tag had already moved to 3.14, where SQLAlchemy 2.0.36 cannot resolve the `Mapped[int | None]` annotations and every database import dies.
- Copy `.env.example` to `.env` and fill in real values before running — `.env` is gitignored and read via `env_file` in the compose file (and by Vite, via `envDir` pointing at the repo root).
- Testing without a real `EFRE_API_KEY`: run `python scripts/mock_llm_server.py`, then start the app with `EFRE_URL` pointed at it (`http://localhost:9000` locally, `http://host.docker.internal:9000` from inside a container). The mock returns fixed transcript/reply/audio values for all three pipeline steps.
- Database: `docker compose up -d db` starts Postgres on 5432. Then `alembic upgrade head` applies the migrations and `python scripts/seed_reference_data.py` fills the reference tables. Both call `load_dotenv()` themselves; `backend/db/session.py` does not — it assembles the connection URL lazily in `build_database_url()`, on the first call to `session_scope()`/`get_engine()`, so importing it never requires an environment. There is **no `DATABASE_URL`**: the URL is built from `POSTGRES_USER`/`POSTGRES_PASSWORD`/`POSTGRES_DB` plus an optional `POSTGRES_HOST`/`POSTGRES_PORT`, which default to `localhost:5432` for host-side calls; the app container gets `POSTGRES_HOST=db` from `compose.yaml`. Alembic uses the same function, so migrations can never run against a different database than the app.
- Schema changes: edit `backend/db/models.py`, then `alembic revision --autogenerate -m "..."`. Constraint and index names come from the naming convention on `Base.metadata` (`backend/db/base.py`, ADR 0036) — never name one by hand, and never remove the convention: without it autogenerate emits unnamed constraints whose `downgrade()` cannot run. Every foreign-key column carries `index=True` (ADR 0035); two tests enforce both rules. Alembic does **not** autodetect `CHECK` constraints — those have to be written into the migration by hand. **Always read the generated migration before applying it** — autogenerate adds `NOT NULL` columns without backfilling, which fails on non-empty tables, and it leaves unique constraints unnamed, which makes `downgrade()` unrunnable. The ER diagram is regenerated automatically on every docs build (see below); `python scripts/generate_erd.py` refreshes `docs/er_modell.png`/`.svg` on demand and needs the Graphviz `dot` binary (`brew install graphviz`).
- Docs site (arc42 + ADRs): `mkdocs serve` (serves on `http://localhost:8000`; stop the app first or pass `-a localhost:8001` to avoid a port clash). `mkdocs build` writes static output to `site/` (gitignored).

- Tests: `pytest`. Every database test creates its own throwaway database on the configured server, migrates it, and drops it afterwards — so Postgres has to be running (`docker compose up -d db`), but the tests never touch the development database. Without a reachable server they skip rather than fail. What they cover: the migration chain in both directions, that every constraint follows the naming convention and every foreign key is indexed, seed idempotency and deactivation, the Session write and read paths, the HTTP endpoints (through httpx's ASGI transport — Starlette 0.35's `TestClient` is incompatible with the pinned httpx 0.28), and that deleting a Session removes its subtree, by ORM and by raw SQL, while leaving reference data alone.
- Deleting a Session removes its subtree through the foreign keys themselves (`ON DELETE CASCADE`, with `passive_deletes=True` on the ORM side), so raw SQL and the ORM behave alike; reference tables deliberately do not cascade. Migrations take a Postgres advisory lock (`backend/db/migrations/env.py`), so two containers starting at once cannot apply the same revision twice.
- Lint: `flake8 .` and `PYTHONPATH=. pylint backend/ scripts/ tests/`. Both are clean and should stay that way. `PYTHONPATH=.` is required — without it pylint cannot resolve the `backend.*` imports and reports nothing but import errors. Generated Alembic revisions are excluded from both (their formatting comes from autogenerate and would be rewritten on every new revision).
